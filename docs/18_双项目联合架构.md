# 双项目联合架构：质量闭环 + 设备上下文

> 日期：2026-11-21 ｜ 面向：投资沟通、付费试点、产品路线 ｜ 状态：联合方案已定义，运行链路尚未打通

## 1. 先说结论

两个项目可以相辅相成，而且组合后的价值明显高于分别演示：

- `UA_LinqInspect` 负责“质检结果可靠进入 MES”，是业务交付的主线；
- `rpi4-opcua-oee-rca-gateway` 负责“设备状态、产量、温度和报警采集”，是 OEE/RCA 的上下文来源；
- 两者通过统一事件契约按 `lineId`、`stationId`、`workOrderId`、`serialNumber` 和时间窗口关联；
- 联合后可以回答客户最关心的一句话：**这批 NG 是否已经进入 MES，同时它和设备停机、温度异常有没有时间上的关联。**

但当前不能宣称已经完成联合产品：两个仓库都能独立运行，尚未共享事件存储、统一时间轴或 OEE/RCA 计算层。

## 2. 为什么当前演示看起来像仪表盘

Node-RED 工作流并没有被删除。它仍在 `nodered/flows.json` 中，包含事件解析、陈旧过滤、去重、报警削峰、单飞行发送、退避、死信、UA 回执校验、指标、健康探针和死信重放，并由完整回归持续启动真实 Node-RED 验证。

上一版“五分钟演示”为了降低首次体验门槛，把重点收窄成了一条 NG 的故障恢复故事，所以前台看起来像可靠性仪表盘。这个取舍适合三分钟投资说明，但不足以表达完整产品形态。

现在演示页已补回两条工作流派：

1. **质检交付主线**：QC 事件 → OPC UA → Node-RED → Edge Core → MES 回执 → UA 写回确认；
2. **设备上下文线**：模拟 PLC → OPC UA 采集 → Gateway → OEE/RCA。

页面明确标注：本次按钮真实执行左线；右线是另一个仓库已具备的采集能力，联合分析仍待接入。

## 3. 两个仓库的职责

| 维度 | UA_LinqInspect | rpi4-opcua-oee-rca-gateway |
|---|---|---|
| 核心问题 | 质检结果如何不丢、不重、可对账地进入 MES | 设备运行、产量、温度与报警如何被稳定采集 |
| 权威数据 | 业务事件、投递状态、MES 回执、死信与审计 | PLC 变量、设备状态、报警事件与采集快照 |
| 当前强项 | SQLite Outbox、状态机、幂等、重试、死信重放、崩溃恢复、安全回归 | 可复现 Mock PLC、原生 OPC UA 事件、订阅重连、结构化网关日志 |
| 当前缺口 | 尚无设备上下文、OEE 和根因分析 | 尚无 OEE/RCA 计算、业务交付与 MES 对账 |
| 适合客户 | 已有视觉/人工质检和 MES、但闭环不可靠的工厂 | 想先做设备数据采集、OEE 和 RCA 试点的工厂 |
| 产品角色 | 质量交付连接器，负责业务闭环 | 设备上下文采集器，负责损失解释 |

## 4. 联合后的完整链路

```text
视觉 / 人工质检                 设备 / PLC
      │                             │
      ▼                             ▼
 QCStation (OPC UA)          MockPLC / Real PLC (OPC UA)
      │                             │
      └──────────┬──────────────────┘
                 ▼
        统一事件与时间轴
   lineId / stationId / workOrderId
   serialNumber / correlationId / occurredAt
                 │
        ┌────────┴────────┐
        ▼                 ▼
 Edge Core 交付链      OEE / RCA 分析
 去重 · 重试 · 死信      A × P × Q
 MES 回执 · UA 写回      时间窗口关联与候选根因
        │                 │
        └────────┬────────┘
                 ▼
     一张可对账的质量与设备损失报告
```

关键原则：**分析层只读，不改变交付状态。** OEE/RCA 可以读事件和回执，但不能替 Edge Core 修改投递状态，也不能根据时间重合直接宣称因果关系。

## 6. 统一事件契约（建议）

```json
{
  "schemaVersion": "1.0",
  "eventId": "evt-...",
  "correlationId": "corr-...",
  "occurredAt": "2026-11-21T06:00:00.000Z",
  "source": "rpi4-gateway",
  "eventType": "PROCESS_CONTEXT",
  "lineId": "JX-LINE-01",
  "stationId": "JX-LINQIN-STATION-01",
  "workOrderId": "WO-JX-20261121-001",
  "serialNumber": "SN-JX-20261121-0001",
  "metrics": {
    "deviceStatus": "RUNNING",
    "currentOutput": 118.4,
    "goodCount": 155,
    "temperatureC": 24.12
  },
  "alarms": []
}
```

业务事件继续使用现有 `NG_ORDER`、`WORK_ORDER_COMPLETED` 等类型。关联时以 `lineId + stationId + workOrderId` 为主，以 `serialNumber` 和 `occurredAt` 为辅助，不把设备报警直接塞进 MES 业务合同。

## 7. OEE 与 RCA 的最小口径

第一版只做一个工位、一个班次窗口，并把每个公式的输入和排除项展示出来：

- Availability = 实际运行时间 / 计划生产时间；
- Performance = 实际产量 / 理论产能；
- Quality = 良品数 / 总产出；
- OEE = Availability × Performance × Quality。

RCA 不做“AI 神谕”，先做可验证的时间窗关联：

1. 取出 NG 前后可配置窗口，例如 ±5 分钟；
2. 关联同工单、同工位、同产线的停机、温度、报警和换型事件；
3. 输出事件重叠、持续时间和影响量，形成候选根因排序；
4. 每条结论必须带原始事件、时间戳和 `correlationId` 证据链；
5. 只表述为“相关/候选原因”，不表述为“已证明因果”。

## 8. 商业化上怎么组合

组合不是把两个项目打包成一个更重的项目，而是形成三个可分开销售的层次：

1. **质量连接器**：先解决不丢、不重、可对账，最容易进入付费试点；
2. **设备上下文包**：接入 PLC 状态、产量、温度和报警，为质量损失提供解释；
3. **OEE/RCA 增值包**：按工位或产线订阅，输出损失分解、候选根因和改善建议。

这样客户可以先买连接器，看到故障恢复和 MES 对账的价值，再为 OEE/RCA 扩容，避免第一单就变成大型 MES 项目。

## 9. 90 天建议路线

### 第 1～2 周：联合 Demo

- 在原演示页增加“设备上下文”一键场景；
- 触发温度异常或停机，同时产生一条 NG；
- 完成真实 Edge Core 投递、MES 回执和 UA 写回；
- 输出简化 OEE 和 RCA 候选根因；
- 联合报告必须能区分模拟数据与真实客户数据。

### 第 3～6 周：单工位付费试点

- 只接一个工位、一种工单、一个 MES 沙箱和一个 PLC 只读点位集；
- 以“故障不丢单、回执可对账、OEE 口径可解释”为验收；
- 不承诺 exactly-once，不承诺无条件自动修复。

### 第 7～12 周：转正式与扩容

- 固化事件契约和适配器；
- 用两个独立客户验证复制性；
- 再决定是否投入真实现场硬件和视觉模块。

## 10. 联合验收指标

| 指标 | 建议门槛 |
|---|---:|
| 质检事件丢失 | 0 条静默丢失 |
| 重复业务开单 | 0 次，依赖业务幂等 |
| MES 回执可对账率 | 100% 有回执或明确死信 |
| 故障后恢复时间 | 试点工位 RTO ≤ 30 秒 |
| OEE 输入可追溯率 | 100% 指标可下钻到原始采样 |
| RCA 证据完整率 | 每个候选根因都有时间、工位、事件和关联 ID |

## 11. 对外表述边界

- 当前是联合方案和演示基础，不是已经完成的双项目生产集成；
- Mock PLC 和 Mock MES 必须明确标注为模拟；
- OEE 结果不能脱离口径、采样窗口和数据质量单独宣传；
- RCA 只能给出相关性和候选原因，不能把时间重合包装成因果证明；
- 正式报价前必须完成真实 MES、真实 PLC 和真实网络环境验证。
