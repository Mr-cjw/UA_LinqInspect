## 2. 启动顺序

### 终端 1：OPC UA Server

```bash
cd ~/UA_LinqInspect
source .node-red/.secure-env
UA_ENDPOINT_PORT=4840 \
UA_SERVER_CERT="$PWD/certs/server/server_cert.der" \
UA_SERVER_PRIVATE_KEY="$PWD/certs/server/server_key.pem" \
UA_TRUSTED_CLIENT_CERTS_DIR="$PWD/certs/trusted_clients" \
UA_ADMIN_USER="$NODERED_OPCUA_USER" \
UA_ADMIN_PASS="$NODERED_OPCUA_PASSWORD" \
QC_AUTO_INSPECT=1 \
QC_NG_PROBABILITY=0.5 \
QC_INSPECT_INTERVAL=1.0 \
.venv/bin/python server/qc_server.py
```

看到以下日志表示成功：

```text
AddressSpace built: ns=2 uri=urn:fde:linqinspect:qc
OPC UA Server listening at opc.tcp://127.0.0.1:4840 (ns=2, policy=Basic256Sha256_SignAndEncrypt)
```

Server 只启用 `Basic256Sha256_SignAndEncrypt`。证书、私钥或信任目录缺失/无效时
会拒绝启动，不会回退到 `NoSecurity`。匿名客户端只能读取；Write 和 Method 必须
使用 `UA_ADMIN_USER` / `UA_ADMIN_PASS` 登录，未配置管理员账号时全站只读。

### 终端 2：Node-RED

```bash
cd ~/UA_LinqInspect
source .node-red/.secure-env
.node-red/node_modules/.bin/node-red \
    --userDir "$PWD/.node-red" --port 1880 --no-telemetry
```

浏览器打开 `http://127.0.0.1:1880`。当前 `.node-red/flows.json` 与 `nodered/flows.json` 一致，正常无需重新导入。

Node-RED 使用独立的 `node-opcua` PKI 目录。若日志出现
`BadCertificateChainIncomplete` 或 `BadCertificateRevocationUnknown`，按
[README 第 2 节](../README.md#2-生成本地-ca-证书首次运行或轮换时) 重新同步 CA 和 CRL，
然后重启 Node-RED。

## 3. 自动化测试预期

### M1 冒烟测试

覆盖：

- namespace = 2
- 初始 Idle
- Idle 完工拒绝
- 三个 EventType 可发现
- StartInspection 成功
- 同工单重复开检幂等
- 不同工单重复开检拒绝且不覆盖
- 虚拟检测产生变量和事件
- NgRate 在窗口内
- SN 写入且事件携带 SN
- 三类事件均携带 `CorrelationId`
- LastMesOrderNo / LastNgMesOrderNo / LastCompletionReceiptNo 可读写
- 只读变量写入被拒
- 错误工单完工被拒
- 正确工单完工、回 Idle、收到完工事件

当前结果：`36/36 passed`。

### M2 正常链路测试

覆盖：

- StartInspection 成功
- DeviceStatus=Running
- NG 事件触发 MES 开单
- `LastNgMesOrderNo` 出现 `MES-*`，`LastMesOrderNo` 同步镜像
- `CurrentWorkOrderId` 未被覆盖
- Server 确实产生 NG 样本
- CompleteWorkOrder 成功
- DeviceStatus 回 Idle
- `LastCompletionReceiptNo` 出现 `RC-*`，`LastMesOrderNo` 同步镜像
- UA 事件关联 ID 与 MES 请求/回执关联 ID 一致
- 请求体携带 `schemaVersion=1.0`

当前结果：`15/15 passed`。

### M2/M3 故障场景测试

`tests/fault_scenarios.py` 覆盖：

- 5xx 连续失败后进入死信，不误写回执；恢复 MES 后完工链路仍可用
- timeout 模式下按 1s/2s/4s 退避，MES 恢复后成功写回
- 4xx 立即死信不重试，429 按 `Retry-After` 退避后死信，非法 2xx 校验失败后死信
- Running 状态下不同工单开检被拒绝，当前工单不被覆盖
- `GET /qc/status` 中队列、死信、MES 模式状态可观察

当前结果：`52/52 passed`。

### MES 长断网与死信重放

`tests/long_outage_recovery.py` 持续注入 MES 5xx，直到单飞行请求耗尽 4 次尝试并进入死信；
随后恢复 MES，验证积压队列自动排空，再通过 `POST /qc/dead-letters/replay` 精确重放该死信。

- 建压期间队列持续增长，长断网不会静默丢弃已入队任务。
- 重试耗尽的事件进入 `MES_UNAVAILABLE` 死信，保留原队列 ID、关联 ID 和请求体。
- 实测恢复排空 RTO 为 `17.95s`，低于测试预算 `30s`。

当前结果：`24/24 passed`。

### 周期 soak

`tests/soak_test.py` 连续执行 6 个工单，每个工单完成开检、完工、回执写回和队列排空，
检查回执唯一、MES 模式稳定、无新增死信且单周期耗时不超过预算。

当前结果：`20/20 passed`，最大单周期 `4.86s`。

### 工位状态持久化与重启

`tests/state_persistence_test.py` 验证快照格式、非法 Running 回退和损坏 JSON 回退；`tests/qc_state_restart_test.py` 在运行中工单产生检测后用 `SIGKILL` 停止 Server，再用同一状态文件重启，验证工单、计数和 SN 序列续增。

当前结果：状态单测 `3/3`，工位状态重启 `11/11`。

### Node-RED 非空队列重启恢复

`tests/restart_recovery.py` 分两阶段执行：

- `seed`：切换到 5xx，制造至少 1 条非空队列，等待 context 落盘后退出。
- `verify`：由一键脚本用同一 userDir 重启 Node-RED，恢复 MES 并检查队列排空、NG/完工回执续写、死信不增加。

当前结果：`18/18 passed`（seed 10 + verify 8）。seed 会先清空旧队列，再确认新工单的 NG 与完工两项都已入队，避免把历史残留误当成恢复证据。

### 短断网恢复

`tests/outage_recovery.py stall` 对 UA Server 执行 5 秒 `SIGSTOP/SIGCONT`，恢复后用新安全会话验证服务仍可开检、产生 NG、完工并写回两类回执。

当前结果：`10/10 passed`。

### 陈旧事件过滤

`tests/outage_recovery.py stale` 注入 2000 年的 NG 事件，验证它不会入队、不会改变去重集合、不会写回 UA 回执，也不会触发 MES 请求。

当前结果：`7/7 passed`。

### UA Server 重启与事件订阅重建

`tests/outage_recovery.py prepare_restart/verify_restart` 记录重启前回执基线，停止并重启 UA Server，等待 Node-RED 日志出现 `[UA重连] Server StartTime 变化`，再验证新工单 NG/完工事件可重新进入 MES。

当前结果：`14/14 passed`（prepare 3 + verify 11）。

## 4. 四个手工验收场景

### 场景① 正常 NG 流

1. 在 Node-RED 点击 `注入:正常`。
2. 点击 `开检 WO-20261109-001`。
3. 等待虚拟质检产生 NG。

应看到：

```text
[入队] NG ...
[回执] MES工单号=MES-... → 写回 LastNgMesOrderNo / LastMesOrderNo
```

UA 变量应满足：

- `LastNgMesOrderNo` 以 `MES-` 开头，`LastMesOrderNo` 与之一致
- `CurrentWorkOrderId` 仍是当前工单

### 场景② MES 超时流

1. 点击 `注入:超时`。
2. 触发一次 NG。

应看到类似：

```text
[重试] ... 1000ms 后第 1 次重试
[重试] ... 2000ms 后第 2 次重试
[重试] ... 4000ms 后第 3 次重试
[回执] MES工单号=...
```

理解点：模拟 MES 的 timeout 模式会在 10 秒后自动恢复；如果持续超时，最终进入死信。

### 场景③ MES 5xx 死信

1. 点击 `注入:5xx`。
2. 触发一次 NG。
3. 等待初始请求 + 3 次退避重试全部失败。

应看到：

```text
[重试] ... 1000ms 后第 1 次重试
[重试] ... 2000ms 后第 2 次重试
[重试] ... 4000ms 后第 3 次重试
[死信FAILED] ... 需人工处置
```

然后点击 `注入:正常`，确认死信不会自动补发。

### 场景④ UA Method 拒绝

方法一：在 Server 运行中重复用不同工单调用 `StartInspection`。

方法二：完工后再次调用 `CompleteWorkOrder`。

应看到：

```text
[UA拒绝] rejected: ... —— 已阻断后续动作
```

重点：拒绝后不应产生任何 MES 开单/报工请求。

## 5. 用 curl 注入 MES 故障

```bash
curl -X POST http://127.0.0.1:1880/inject/inj_ok
curl -X POST http://127.0.0.1:1880/inject/inj_5xx
```

队列、死信、去重集合和运行计数位于 SQLite，默认 `data/qc-queue.sqlite`。MES 模式、最近请求/响应等运行态仍可在 flow context 中。先执行一次正常测试，再检查数据库：

```bash
python3 - <<'PY'
import sqlite3
db = sqlite3.connect('data/qc-queue.sqlite')
print('queue', db.execute('select status, count(*) from queue group by status').fetchall())
print('dead', db.execute('select count(*) from dead_letters').fetchone()[0])
print('dedup', db.execute('select kind, count(*) from dedup group by kind').fetchall())
print('metrics', db.execute('select name,type,outcome,error_code,value from metrics order by name').fetchall())
PY
```

正常空闲时应看到 `queue` 无记录、`dead` 不超过 100、`dedup` 按 `ng_fp/ng_sn/done` 分类计数。

运行指标：

```bash
curl -s http://127.0.0.1:1880/qc/status | jq
curl -s http://127.0.0.1:1880/metrics | head -40
```

数据库使用 WAL，在线备份应使用 SQLite backup API，不要只复制主文件：

```bash
.venv/bin/python scripts/backup_queue.py --keep 7
```

脚本会先备份到临时文件，执行 `integrity_check`/`foreign_key_check`，再原子落盘。当前是“至少一次投递 + 接收端幂等”，不宣称 exactly-once。

## 7. 常见问题与排查

### 7.1 `listen EPERM: operation not permitted 0.0.0.0:1880`

这是运行环境沙箱禁止监听端口，不是 Node-RED 配置错误。需要在允许网络访问的终端中启动，或按当前环境要求提权运行。

### 7.2 `asyncua` 导入失败

确认使用虚拟环境：

```bash
.venv/bin/python -c 'import asyncua; print(asyncua.__version__)'
```

预期输出 `2.1.0`。不要使用系统 Python。

### 7.3 PyPI 连接失败

如果出现 `ProxyError` 或 `Network is unreachable`，是网络受限。开放网络后执行：

```bash
.venv/bin/python -m pip install -r server/requirements.txt
```

### 7.4 Node-RED 连不上 UA

检查：

1. 4840 是否有 Server 监听。
2. `ep1` 的 Endpoint 是否为 `opc.tcp://localhost:4840`。
3. 安全策略是否为 `Basic256Sha256`，安全模式是否为 `SignAndEncrypt`。
4. 客户端证书/私钥是否指向 `certs/client/`，CA 与 CRL 是否已同步到 Node-RED 的 PKI 目录。
5. Server 是否已打印 `OPC UA Server listening at opc.tcp://...`。

### 7.5 事件订阅没有数据

检查：

1. Node-RED 是否部署了最新 `flows.json`。
2. `opcea` 是否显式订阅 `ns=2;s=NgDetectedEventType`。
3. `opcea_done` 是否显式订阅 `ns=2;s=WorkOrderCompletedEventType`。
4. 是否保留了 5 秒重发订阅逻辑（`fn_sub_log_ng` / `fn_sub_log_done`）。

### 7.6 Method 调用返回空或参数错误

`node-red-contrib-opcua` 的 Method 入参必须放在：

```javascript
msg.inputArguments = [{ dataType: 'String', value: wo }];
```

不是 `payload.inputArguments`，也不是 `callmethod`。

### 7.7 写回执变量失败

检查是否使用 `.node-red/flows.json` 中的 `opcua` 节点；`LastMesOrderNo`、`LastNgMesOrderNo`、`LastCompletionReceiptNo` 在 Server 中都必须是 ReadWrite。可用 `tests/_perm_probe.py` 查看 AccessLevel。

### 7.8 回执变量没有变化

检查顺序：

1. MES 是否返回 `mesOrderNo` / `receiptNo`。
2. `fn_resp` 是否成功匹配队列项。
3. `opcua` 节点是否收到两条 `action=write` 消息。
4. `fn_ua_result` 是否打印写回成功。

### 7.9 队列重启后是否还在

优先运行 `.venv/bin/python scripts/run_regression.py`，其中的 `restart_recovery_seed/verify` 和 `crash_recovery_prepare/verify` 会自动验证正常重启与 `SIGKILL` 崩溃恢复。手工排查时再检查：

检查：

```bash
ls -l data/qc-queue.sqlite*
python3 - <<'PY'
import sqlite3
db = sqlite3.connect('data/qc-queue.sqlite')
print(db.execute('pragma integrity_check').fetchone())
print(db.execute('select id,status,attempts from queue order by seq').fetchall())
PY
```

如果默认数据库不存在，确认 Node-RED 使用仓库内的 `nodered/settings.js` 启动模板；配置通过
`functionGlobalContext` 注入 `qstore`/`qlogic`。回归环境使用独立 `QC_DB_PATH`，不会污染本地数据库。

若队列项长期停在 `SENDING`，检查 Node-RED 是否仍在运行，并等待 15 秒看门狗触发；若持续卡住，
检查 `node-red.log` 中的 `[SQLite发送泵失败]`、`[SQLite响应查询失败]` 和 `[SQLite重试事务失败]`。

### 7.10 端口被占用

```bash
ss -ltnp | grep -E ':(4840|1880)'
```

先停止占用进程，再启动项目。不要同时启动多个 Server/Node-RED 实例。

### 7.11 换机器后为什么 `.conda` 不能用

`.conda` 是 Windows 版 Python 目录，包含 `python.exe`，不是 Linux 可执行环境。Ubuntu 使用 `.venv`。需要重建时：

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r server/requirements.txt
```

### 7.12 UA Server 重启后读写正常，但收不到事件

读写心跳成功只说明普通 Session/Channel 已恢复，不代表旧 Event Subscription 仍绑定在新 Server Session 上。检查 Node-RED 日志是否出现：

```text
[UA重连] Server StartTime 变化：... -> ...，重建事件订阅与读写会话
```

该日志由心跳读取标准变量 `ServerStatus.StartTime`（`ns=0;i=2257`）触发。若 StartTime 读取失败，先确认日志中的 `[UA健康] ServerStatus.StartTime 无法解析` 或 UA 读取错误；修复后重启 Node-RED 并重新跑 `scripts/run_regression.py`。

## 8. 干净停止

两个服务分别按 `Ctrl+C`。确认端口释放：

```bash
ss -ltnp | grep -E ':(4840|1880)' || echo 'ports free'
```
