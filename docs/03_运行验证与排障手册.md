## 2. 启动顺序

### 终端 1：OPC UA Server

```bash
cd ~/UA_LinqInspect
UA_ENDPOINT_PORT=4840 \
UA_SERVER_CERT="$PWD/certs/server/server_cert.der" \
UA_SERVER_PRIVATE_KEY="$PWD/certs/server/server_key.pem" \
UA_TRUSTED_CLIENT_CERTS_DIR="$PWD/certs/trusted_clients" \
UA_ADMIN_USER=admin \
UA_ADMIN_PASS='replace-with-a-strong-password' \
QC_AUTO_INSPECT=1 \
QC_NG_PROBABILITY=0.5 \
QC_INSPECT_INTERVAL=1.0 \
.venv/bin/python server/qc_server.py
```

看到以下日志表示成功：

```text
AddressSpace built: ns=2 uri=urn:fde:linqinspect:qc
OPC UA Server listening at opc.tcp://127.0.0.1:4840 (ns=2, policy=Basic256Sha256_SignAndEncrypt)
```

Server 只启用 `Basic256Sha256_SignAndEncrypt`。证书、私钥或信任目录缺失/无效时
会拒绝启动，不会回退到 `NoSecurity`。匿名客户端只能读取；Write 和 Method 必须
使用 `UA_ADMIN_USER` / `UA_ADMIN_PASS` 登录，未配置管理员账号时全站只读。

### 终端 2：Node-RED

```bash
cd ~/UA_LinqInspect
.node-red/node_modules/.bin/node-red \
    --userDir "$PWD/.node-red" --port 1880 --no-telemetry
```

浏览器打开 `http://127.0.0.1:1880`。当前 `.node-red/flows.json` 与 `nodered/flows.json` 一致，正常无需重新导入。

Node-RED 使用独立的 `node-opcua` PKI 目录。若日志出现
`BadCertificateChainIncomplete` 或 `BadCertificateRevocationUnknown`，按
[README 第 2 节](../README.md#2-生成本地-ca-证书首次运行或轮换时) 重新同步 CA 和 CRL，
然后重启 Node-RED。

## 4. 四个手工验收场景

### 场景① 正常 NG 流

1. 在 Node-RED 点击 `注入:正常`。
2. 点击 `开检 WO-20261109-001`。
3. 等待虚拟质检产生 NG。

应看到：

```text
[入队] NG ...
[回执] MES工单号=MES-... → 写回 LastNgMesOrderNo / LastMesOrderNo
```

UA 变量应满足：

- `LastNgMesOrderNo` 以 `MES-` 开头，`LastMesOrderNo` 与之一致
- `CurrentWorkOrderId` 仍是当前工单

### 场景② MES 超时流

1. 点击 `注入:超时`。
2. 触发一次 NG。

应看到类似：

```text
[重试] ... 1000ms 后第 1 次重试
[重试] ... 2000ms 后第 2 次重试
[重试] ... 4000ms 后第 3 次重试
[回执] MES工单号=...
```

理解点：模拟 MES 的 timeout 模式会在 10 秒后自动恢复；如果持续超时，最终进入死信。

### 场景③ MES 5xx 死信

1. 点击 `注入:5xx`。
2. 触发一次 NG。
3. 等待初始请求 + 3 次退避重试全部失败。

应看到：

```text
[重试] ... 1000ms 后第 1 次重试
[重试] ... 2000ms 后第 2 次重试
[重试] ... 4000ms 后第 3 次重试
[死信FAILED] ... 需人工处置
```

然后点击 `注入:正常`，确认死信不会自动补发。

### 场景④ UA Method 拒绝

方法一：在 Server 运行中重复用不同工单调用 `StartInspection`。

方法二：完工后再次调用 `CompleteWorkOrder`。

应看到：

```text
[UA拒绝] rejected: ... —— 已阻断后续动作
```

重点：拒绝后不应产生任何 MES 开单/报工请求。

## 5. 用 curl 注入 MES 故障

```bash
curl -X POST http://127.0.0.1:1880/inject/inj_ok
curl -X POST http://127.0.0.1:1880/inject/inj_5xx
curl -X POST http://127.0.0.1:1880/inject/inj_to
```

flow context 使用 localfilesystem 持久化，状态文件位于 `.node-red/context/qcflow/flow.json`。先执行一次正常测试，再检查文件中的 `buf`、`dead`、`mesMode`。若此前队列为空，正常重启后应看到：

```text
mesMode = ok
buf = []
dead = []
ngSeen / snSeen / doneSeen = {}
```

注意：文件 context 不等于事务型队列。Node-RED 重启后“非空队列恢复且不重复开单/报工”尚未纳入自动化测试，工厂试点前必须用 SQLite 或独立边缘服务补上。

## 7. 常见问题与排查

### 7.1 `listen EPERM: operation not permitted 0.0.0.0:1880`

这是运行环境沙箱禁止监听端口，不是 Node-RED 配置错误。需要在允许网络访问的终端中启动，或按当前环境要求提权运行。

### 7.2 `asyncua` 导入失败

确认使用虚拟环境：

```bash
.venv/bin/python -c 'import asyncua; print(asyncua.__version__)'
```

预期输出 `2.1.0`。不要使用系统 Python。

### 7.3 PyPI 连接失败

如果出现 `ProxyError` 或 `Network is unreachable`，是网络受限。开放网络后执行：

```bash
.venv/bin/python -m pip install -r server/requirements.txt
```

### 7.4 Node-RED 连不上 UA

检查：

1. 4840 是否有 Server 监听。
2. `ep1` 的 Endpoint 是否为 `opc.tcp://localhost:4840`。
3. 安全策略是否为 `Basic256Sha256`，安全模式是否为 `SignAndEncrypt`。
4. 客户端证书/私钥是否指向 `certs/client/`，CA 与 CRL 是否已同步到 Node-RED 的 PKI 目录。
5. Server 是否已打印 `OPC UA Server listening at opc.tcp://...`。

### 7.5 事件订阅没有数据

检查：

1. Node-RED 是否部署了最新 `flows.json`。
2. `opcea` 是否显式订阅 `ns=2;s=NgDetectedEventType`。
3. `opcea_done` 是否显式订阅 `ns=2;s=WorkOrderCompletedEventType`。
4. 是否保留了 5 秒重发订阅逻辑（`fn_sub_log_ng` / `fn_sub_log_done`）。

### 7.6 Method 调用返回空或参数错误

`node-red-contrib-opcua` 的 Method 入参必须放在：

```javascript
msg.inputArguments = [{ dataType: 'String', value: wo }];
```

不是 `payload.inputArguments`，也不是 `callmethod`。

### 7.7 写回执变量失败

检查是否使用 `.node-red/flows.json` 中的 `opcua` 节点；`LastMesOrderNo`、`LastNgMesOrderNo`、`LastCompletionReceiptNo` 在 Server 中都必须是 ReadWrite。可用 `tests/_perm_probe.py` 查看 AccessLevel。

### 7.8 回执变量没有变化

检查顺序：

1. MES 是否返回 `mesOrderNo` / `receiptNo`。
2. `fn_resp` 是否成功匹配队列项。
3. `opcua` 节点是否收到两条 `action=write` 消息。
4. `fn_ua_result` 是否打印写回成功。

### 7.9 队列重启后是否还在

检查：

```bash
find .node-red/context -maxdepth 3 -type f -print
jq 'keys' .node-red/context/qcflow/flow.json
```

如果目录不存在，说明 `.node-red/settings.js` 没有启用 `contextStorage`。配置应包含：

```javascript
contextStorage: {
    default: {
        module: "localfilesystem",
        config: { base: "context", cache: true, flushInterval: 1 }
    }
}
```

不要将 `cache` 设为 `false`：当前 Function 节点使用同步 `flow.get()`，Node-RED 会报 `File Store cache disabled - only asynchronous access supported`。

### 7.10 端口被占用

```bash
ss -ltnp | grep -E ':(4840|1880)'
```

先停止占用进程，再启动项目。不要同时启动多个 Server/Node-RED 实例。

### 7.11 换机器后为什么 `.conda` 不能用

`.conda` 是 Windows 版 Python 目录，包含 `python.exe`，不是 Linux 可执行环境。Ubuntu 使用 `.venv`。需要重建时：

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r server/requirements.txt
```

## 8. 干净停止

两个服务分别按 `Ctrl+C`。确认端口释放：

```bash
ss -ltnp | grep -E ':(4840|1880)' || echo 'ports free'
```
