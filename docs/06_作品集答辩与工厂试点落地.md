# 作品集答辩与工厂试点落地

这份文档解决两个容易混在一起的问题：

- **作品集/答辩**：如何在有限时间里讲清问题、取舍、证据和边界。
- **工厂试点**：如何从可运行原型走到可被现场接受的单站试点。

共同原则：**不把 PoC 说成生产系统，也不把真实工程问题藏起来。**

## 1. 一套统一叙事

不要用“我做了个 OPC UA Demo”开场。更准确的开场是：

> 我做的是一条单工位质检闭环：虚拟 AI 结果通过 OPC UA 信息模型和事件进入边缘层，Node-RED 负责去重、缓冲、重试和死信，再调用模拟 MES 完成开单/报工，并把分类回执写回 UA。重点不是界面，而是设备语义、工单状态和失败处置。

这条叙事同时适用于答辩和试点，因为两者关心的核心一致：

| 核心问题 | 答辩想看什么 | 工厂想看什么 |
|---|---|---|
| 为什么需要 OPC UA | 是否理解语义模型、Method、Event | 是否能接入现有 OT 资产 |
| 为什么需要边缘层 | 是否理解解耦与可靠性 | 断网/MES 抖动时是否可处置 |
| 为什么拆回执变量 | 是否理解业务语义边界 | 追溯、审计、对账是否清楚 |
| 为什么有测试 | 是否能证明而非只演示 | 是否敢在产线旁试运行 |

## 2. 作品集答辩：5 分钟演示顺序

### 2.1 演示脚本

1. **20 秒讲定位**：单工位质检 OT-IT 闭环原型，不是完整 MES/SCADA。
2. **50 秒看模型**：UaExpert 展示 `QCStation` 对象树、15 个变量、3 个 Method、3 个 EventType。
3. **80 秒跑正常链路**：开检 → NG 事件 → Node-RED 入队 → 模拟 MES 回执 → `LastNgMesOrderNo` 与镜像更新。
4. **80 秒跑失败链路**：注入 5xx → 退避 → 死信 → `/qc/status` 可见 → 恢复 MES 后新任务仍能成功。
5. **50 秒讲边界**：NoSecurity、模拟 MES、单工位、flow context 非事务队列、M3 断网重连未自动化。
6. **20 秒收束**：下一步是 correlationId、SQLite 事务队列、证书与真实 MES 沙箱。

### 2.2 必须准备的证据

- `tests/smoke_test.py`：33/33 PASS。
- `tests/nodered_e2e.py`：10/10 PASS。
- `tests/fault_scenarios.py`：19/19 PASS。
- 一段 2~3 分钟录屏：正常 NG、5xx 死信、状态接口、UA 变量变化。
- 一张手画链路图：UA → Node-RED → MES → UA 回执。
- 一张对照表：`CurrentWorkOrderId`、`LastNgMesOrderNo`、`LastCompletionReceiptNo`、`LastMesOrderNo` 的语义。

### 2.3 最容易被追问的点

1. **“这不就是 Node-RED 转发 HTTP 吗？”**
   回答：转发只是最外层；真正的工作是 UA 语义模型、Method 前置校验、事件订阅、单飞行队列、退避/死信、双侧防重和回执语义分离。
2. **“为什么不用 MQTT？”**
   回答：当前需要的是设备语义、Method 和 Event。高频遥测可后续引入 MQTT/Sparkplug B，但不应用来替代控制面。
3. **“断网会不会丢数据？”**
   回答：当前 flow context 近实时落盘，降低重启丢失风险，但不是事务型 exactly-once；工厂试点前换 SQLite 或独立边缘队列并做重启/断电测试。
4. **“AI 准确率多少？”**
   回答：当前是虚拟数据源，没有真实模型指标；接真实 YOLOv8 后必须补标注集、误检/漏检、漂移和模型版本治理。
5. **“能直接上产线吗？”**
   回答：不能。当前是试点前基线，缺少证书/角色、真实 MES 契约、事务队列、审计和现场网络验证。

完整问答见 [04_掌握检查与答辩问答.md](04_掌握检查与答辩问答.md)。

## 3. 工厂试点：先限定问题，再谈扩产

### 3.1 建议的试点边界

第一轮只做一个工位、一个产品族、一种工单类型，且**只读/影子运行优先**：

| 阶段 | 行为 | 退出条件 |
|---|---|---|
| A. 影子运行 | 质检结果照常产生，只记录拟发送的 MES 报文，不真正开单/报工 | 连续运行 48~72h；日志可对账；无未解释的队列积压 |
| B. 人工确认闭环 | 操作员确认后才写 MES；异常可暂停 | 20~50 个真实工单；重复开单为 0；回执与 MES 日志一致 |
| C. 单站自动闭环 | 正常路径自动开单/报工，死信必须人工处置 | 双方签收验收口径；安全/网络/审计通过评审 |

不要从“全产线自动控制”开始。单站闭环跑不稳，扩多站只会放大问题。

### 3.2 试点前必须补齐的能力

1. **安全**：OPC UA 证书、信任列表、匿名只读、写操作角色分离。
2. **真实契约**：MES 接口文档、字段字典、错误码、幂等键、超时与限流规则。
3. **事务队列**：SQLite 或独立边缘服务；重启、断电、重复请求可恢复。
4. **关联标识**：`correlationId` 贯穿 UA 事件、Node-RED 日志、MES 请求与回执。
5. **可观测性**：队列深度、最老任务年龄、死信数、重试数、成功率、心跳失败。
6. **现场 runbook**：断网、MES 维护、死信处置、班次切换、数据保留和回滚步骤。
7. **AI 证据链**：模型版本、阈值、图像 URI、标注集版本、误检/漏检统计。

### 3.3 试点成功指标（建议）

| 指标 | 建议口径 | 试点目标 |
|---|---|---|
| 报文成功率 | MES 2xx / 应发送事件 | ≥ 99.5%（稳定网络下） |
| 回执一致率 | UA 回执与 MES 记录可逐笔对上 | 100% |
| 重复开单率 | 重复业务单 / 总业务单 | 0 |
| 死信率 | 进入死信的任务 / 总任务 | 可解释、可处置，不设虚假 0 目标 |
| 积压恢复 | 断网恢复后队列清空时间 | 分钟级，满足现场节拍 |
| 重复/丢失 | 重启与重试场景 | 不得出现未解释的重复或丢失 |
| 质检指标 | 误检率/漏检率/节拍开销 | 由真实模型和产线共同定义 |

指标必须先和工厂、MES 团队确认口径，不能只在自己脚本里“通过”。

## 4. 对标同行：借鉴模式，不照搬产品

本项目不应和完整商业平台比功能数量，而应比“单站闭环是否讲透、失败是否可处置”。

| 参照类型 | 代表能力 | 本项目现状 | 可借鉴 | 不照搬 |
|---|---|---|---|---|
| OPC UA 网关（KEPServerEX、Matrikon 等） | 多协议接入、Tag 管理、诊断、冗余 | 单一 asyncua Server | 标准地址空间、连接诊断、重连可观测 | 一开始堆几十种驱动 |
| SCADA/UNS（Ignition、HighByte、HiveMQ 等） | Unified Namespace、历史库、告警、南北向集成 | UA 事件 + HTTP MES | 统一命名、状态模型、MQTT Sparkplug B 北向遥测 | 在 PoC 阶段上完整 SCADA/UNS 平台 |
| 边缘平台（Azure IoT Edge、AWS Greengrass 等） | 模块生命周期、离线缓冲、设备身份、OTA | 本机 Node-RED + flow context | 边缘服务化、健康检查、配置版本、OTA 思路 | 为了“云原生”增加部署复杂度 |
| MES（SAP DM/ME、Siemens Opcenter 等） | ISA-95、工单生命周期、 genealogy、事务与审计 | 模拟 MES + 单工位状态机 | 工单状态机、幂等事务、追溯链、审计 | 自己实现完整 MES |
| OPC UA 生态（open62541、UA .NET、asyncua） | 安全、PubSub、Alarm & Condition、Historical Access | Client/Server + Event | 证书、角色、A&C、历史访问 | 无场景地替换现有栈 |

### 4.1 最值得借鉴的三个方向

1. **Unified Namespace 思路**：先统一对象/工单/设备命名，再谈接入数量。
2. **Store-and-forward 边缘模式**：本地先落盘，再按确认/重试/死信状态机补传。
3. **MES 的事务语义**：请求必须有业务幂等键、稳定错误码和可对账回执，而不是“HTTP 200 就算成功”。

### 4.2 当前最真实的三个差距

1. **没有事务型持久化**：flow context 适合原型，不足以支撑断电/崩溃后的 exactly-once 讨论。
2. **没有真实安全边界**：NoSecurity 只能用于隔离实验环境。
3. **没有真实模型与产线数据**：当前 AI 部分是可替换的仿真数据源，不能宣称质检效果。

## 5. 30/60/90 天路线

### 0~30 天：把证据补硬

- `correlationId` 贯穿全链路。
- MES 错误分类：4xx 不重试、429 按 `Retry-After`、5xx/timeout 退避。
- 一键回归脚本：M1 + M2 + 故障场景。
- Node-RED 非空队列重启恢复测试。
- `/qc/status` 增加队列年龄、成功率、重试/死信指标。

### 31~60 天：达到试点准入

- SQLite/独立边缘服务事务队列。
- OPC UA 证书、信任列表、写权限角色。
- 真实 MES 沙箱联调，补 `schemaVersion`、稳定 `errorCode`、`X-Correlation-Id`。
- 结构化日志与集中采集；补 runbook 和回滚步骤。

### 61~90 天：单站影子/受控试点

- 接入真实 YOLOv8/ONNX 推理与产线 SN。
- 影子运行 48~72h，逐笔对账。
- 人工确认闭环 20~50 单。
- 评审通过后进入单站自动闭环，死信保持人工处置。

## 6. 答辩与试点都不要说的话

- “已经完全达到生产级。”
- “重启/断网绝对不会丢数据。”
- “AI 质检准确率很高”，但拿不出真实标注集和指标。
- “MES 已经对接”，但只是自己写的 HTTP 模拟端。
- “HTTP 200 就是 MES 已入库”，没有对账与回执语义。

## 7. 下一步最值得做的一件事

如果只能做一项：**先做 `correlationId` + SQLite 事务队列 + 重启恢复测试**。

原因：它同时提升作品集的“工程可信度”和工厂试点的“现场可用性”，而且能被自动化测试客观证明。安全证书排在其后，因为试点前两者都必须完成。
