# 状态源重构与持久化恢复

> 日期：2026-11-21 ｜ 当前证据：`.tmp/regression-20261120-171127/summary.json` ｜ 一键回归：23 个测试模块、378 项断言/用例通过

## 1. 本轮完成了什么

本轮完成的是“工位控制状态单写者 + 可恢复持久化”的垂直切片，不是整套 Edge Core 替换：

- `DeviceStatus`、`CurrentWorkOrderId`、`CurrentPartSN` 改为外部只读，只能由 Server 内受控状态迁移或检测入口更新。
- `StartInspection`、`CompleteWorkOrder`、`ResetCounters` 和 `record_inspection` 共用同一把进程内异步锁，避免检测结果与完工并发交错。
- 工单、计数器、滑动窗口、SN 日序列和最近检测结果写入版本化 JSON 快照。
- 服务启动时恢复快照；进程重启后不静默把工单、计数和 SN 归零。
- 新增真实 `SIGKILL` 重启测试，验证运行中工单、计数、SN 序列续增和完工能力。

MES 投递队列仍由 Node-RED 的 SQLite WAL 事务队列承载。它和 OPC UA Server 的控制状态目前是两个明确的持久化边界；本轮的成果是把工位状态从纯内存提升为可恢复状态，并未宣称两者已经收敛为同一事务。

## 2. 状态所有权

| 状态 | 当前权威来源 | 写入方式 | 恢复方式 |
|---|---|---|---|
| 设备状态、当前工单、目标数 | `QCStation` + `QC_STATE_PATH` 快照 | `StartInspection` / `CompleteWorkOrder` | 启动时读取快照 |
| 检测计数、OK/NG 数、滑动窗口 | `QCStation` + `QC_STATE_PATH` 快照 | `record_inspection` / `ResetCounters` | 启动时读取快照 |
| 当前 SN、SN 日序号 | `QCStation` + `QC_STATE_PATH` 快照 | Server 检测入口 | 启动时读取快照并继续递增 |
| MES 队列、去重、死信、投递指标 | Node-RED SQLite WAL | Node-RED 事务 | SQLite 重启恢复 |
| MES 回执展示变量 | OPC UA 变量 | Node-RED 回写 | Node-RED 队列恢复后继续回写 |
| 可视化编排与操作界面 | Node-RED | 操作员/受保护 HTTP | flow 文件与 SQLite 状态 |

三个 MES 回执变量 `LastMesOrderNo`、`LastNgMesOrderNo`、`LastCompletionReceiptNo` 仍允许 Node-RED 写入；本次收紧的是工单控制和单件追溯变量，不能把当前实现表述为“所有 UA 变量都只读”。

## 3. 状态机规则

### 3.1 工单迁移

| 当前状态 | 输入 | 结果 |
|---|---|---|
| Idle | 非空 `workOrderId` 且 `targetCount > 0` | 进入 Running，绑定工单和目标数 |
| Running | 同一 `workOrderId` 再次 `StartInspection` | 幂等接受，状态不重置 |
| Running | 不同 `workOrderId` | 拒绝，不覆盖当前工单 |
| Fault | `StartInspection` | 拒绝 |
| Running | 正确的 `CompleteWorkOrder` | 发出完工事件，回到 Idle，清空工单与目标数 |
| 非 Running / 工单不一致 | `CompleteWorkOrder` | 拒绝，不修改状态 |
| 非 Running | `record_inspection` | 丢弃，并返回未接受 |

### 3.2 并发与一致性

- 所有会修改工位业务状态的入口先取得同一把 `asyncio.Lock`。
- 完工事件发出后，迟到的检测结果无法再挂到已结束工单。
- 每次状态变更完成后再持久化；持久化使用异步线程执行文件 `fsync`，避免阻塞 OPC UA 事件循环和订阅发布。
- 同一进程内是单写者；当前不支持多个 Server 进程同时写同一个状态文件。

## 4. 持久化格式与恢复语义

状态文件使用 `schemaVersion: 1`，包含：

- 工单与设备状态；
- 目标数、检测总数、OK/NG 数；
- 最近滑动窗口；
- 当前 SN、SN 日期和序号；
- 最近结果、缺陷、置信度、图像号和时间戳。

写入流程：

```text
构造不可变快照
  -> 写同目录临时文件
  -> flush + fsync
  -> os.replace 原子替换
  -> fsync 父目录（尽力而为）
```

恢复规则：

- 文件不存在：使用默认 Idle 状态。
- JSON 损坏或 schema 不兼容：记录告警并回退默认状态，不中断服务启动。
- Running 状态缺少工单：回退 Idle，避免无法完工的悬挂状态。
- 计数和窗口做边界清洗；置信度限制在 0–1。

`SIGKILL` 恢复测试验证了：

1. 崩溃前处于 Running 的工单和计数可以从快照恢复；
2. 服务重启后仍能识别当前工单；
3. 新 SN 从持久化序号继续递增，而不是回到 `000001`；
4. 恢复后的工单可以调用 `CompleteWorkOrder` 回到 Idle。

## 6. 明确边界

- **不是零数据丢失**：进程可能在“业务状态已改变、快照尚未落盘”的极短窗口内被杀，最坏情况可能丢失最后一次尚未完成持久化的检测更新。当前没有与 MES 队列共享事务。
- **不是多进程安全**：锁只覆盖单进程；多 Server 实例同时写同一文件会产生覆盖风险。
- **不是 Edge Core 已替换 Node-RED**：外部 Edge Core 垂直切片和在线 Node-RED 队列仍并存，尚未统一为一个控制面。
- **不是 exactly-once**：MES 投递仍是 at-least-once + 接收端幂等，必须保留这一合同口径。
- **不是生产级存储方案**：JSON 快照适合单工位试点与恢复基线，不适合多工位、多租户或高并发写入。

## 7. 后续计划

1. 把工位控制状态与队列状态收敛到同一个 SQLite 事务边界，优先统一 `workOrderId + correlationId + deliveryId` 的关联关系。
2. 明确零检测完工、超额检测、重复工单 `attemptId` 和目标数到达后的状态语义。
3. 增加磁盘满、权限错误、状态文件回滚和备份恢复演练。
4. 把 Node-RED 在线发送泵迁移到 Edge Core 适配器，Node-RED 只保留编排和操作界面。
5. 在真实 MES 沙箱和现场负载下复验恢复时间、回执对账率和状态一致性。
