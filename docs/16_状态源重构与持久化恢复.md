# 状态源重构与持久化恢复

> 日期：2026-11-22 ｜ 最终证据：`.tmp/regression-20261122-085628/summary.json` ｜ 一键回归：43 个测试模块、682 项断言/用例通过

## 1. 本轮完成了什么

本轮完成的是“工位状态 + 事件 Outbox 同事务持久化”，并将它与 Node-RED 投递队列放到同一个 SQLite 数据库中：

- `DeviceStatus`、`CurrentWorkOrderId`、`CurrentPartSN` 和全部 MES 回执变量对外只读。
- 工单控制只能通过 Method 修改；MES 回执只能通过 `RecordMesReceipt` 修改。
- `StartInspection`、`CompleteWorkOrder`、`ResetCounters` 和 `record_inspection` 共用同一把进程内锁。
- 工位快照与 NG/完工事件 Outbox 写入同一 SQLite 行/事务，不再依赖 JSON 文件作为试点默认状态源。
- Node-RED 通过 UA 事件重发接收 Outbox，在事件成功进入 SQLite 投递队列后调用 `AcknowledgeEvent`。
- SQLite 队列与工位状态使用同一个 `QC_DB_PATH` 文件；状态快照、Outbox、队列、去重、死信和 UA 写回状态可以整体备份与恢复。
- 旧 JSON 状态可在第一次 SQLite 启动时迁移，包括未确认 Outbox。
- 新增真实 `SIGKILL` 测试，验证工单、计数、SN 序列和未确认事件可恢复。
- 保存失败时回滚内存状态并尽力重同步 UA 变量，避免内存状态领先于 SQLite 已提交状态。

实际链路是标准 transactional outbox：

```text
受控状态迁移
  -> SQLite 同事务提交状态快照 + 待确认事件
  -> Server 周期重发未确认事件
  -> Node-RED 幂等写入 SQLite 投递队列
  -> AcknowledgeEvent 删除 Outbox 项
  -> MES 投递与 UA 回执写回确认
```

这不是跨进程单一事务：状态+Outbox 是一个事务，Node-RED 队列写入是下游幂等事务；因此仍不能宣称 exactly-once。

## 2. 状态所有权

| 状态 | 当前权威来源 | 写入方式 | 恢复方式 |
|---|---|---|---|
| 设备状态、当前工单、目标数 | SQLite `qc_station_state` | Method 状态机 | 启动时读取 SQLite |
| 检测计数、OK/NG 数、滑动窗口 | SQLite `qc_station_state` | 检测入口 / `ResetCounters` | 启动时读取 SQLite |
| 当前 SN、SN 日序号 | SQLite `qc_station_state` | Server 检测入口 | 启动时读取并继续递增 |
| NG/完工未确认事件 | SQLite 状态行中的 `outbox_json` | 与状态同事务提交；ACK 后删除 | 启动后重发，直到 ACK |
| MES 队列、去重、死信、UA 写回 | 同一 SQLite 文件中的 Node-RED 表 | Node-RED 事务 | SQLite 重启恢复 |
| MES 回执展示变量 | OPC UA 变量 | 仅 `RecordMesReceipt` Method | 由调用方在投递成功后写入并回读确认 |
| 可视化编排与操作界面 | Node-RED | 受保护 HTTP / 操作员 | flow 文件与 SQLite 状态 |

## 3. 状态机规则

| 当前状态 | 输入 | 结果 |
|---|---|---|
| Idle | 非空 `workOrderId` 且 `targetCount > 0`，Outbox 未到高水位 | 进入 Running |
| Running | 同一工单再次 `StartInspection` | 幂等接受，不重置状态 |
| Running | 不同工单 | 拒绝，不覆盖当前工单 |
| Fault | `StartInspection` | 拒绝 |
| Running | 正确工单 `CompleteWorkOrder` | 提交 Idle + 完工 Outbox |
| 非 Running / 工单不一致 | `CompleteWorkOrder` | 拒绝 |
| 非 Running | `record_inspection` | 丢弃 |
| Outbox 达到高水位 | 新开检 | 拒绝并提示先 ACK 或受控清空 |
| Outbox 达到硬上限 | 检测 / 完工 | 拒绝，不静默丢弃事件 |

所有状态变更都在进程内锁内完成。Outbox 达到高水位或硬上限时失败关闭，而不是删除旧事件为新事件腾空间。

## 4. SQLite 持久化与 Outbox

`qc_station_state` 每个工位一行，包含：

- 工单、设备状态、目标数；
- 检测总数、OK/NG 数、滑动窗口；
- 当前 SN、SN 日期和序号；
- 最近结果、缺陷、置信度、图像号、时间戳；
- `outbox_json`：尚未 ACK 的事件数组；
- `updated_at`。

事件结构包含：

- `eventVersion`、稳定 `eventId`；
- `eventType`：`ng` / `done`；
- 业务字段、`CorrelationId`、`SourceEventId`；
- 严重级别、消息和创建时间。

一致性规则：

1. 状态与 Outbox 在一个 `BEGIN IMMEDIATE` 事务内 upsert。
2. 写入失败时旧 SQLite 状态保持不动；进程内状态回退到上一份已提交快照，并尽力重同步 UA 变量后继续上抛原异常。
3. Node-RED 只有在队列事务成功（新入队或已存在去重记录）后才 ACK。
4. 未 ACK 事件按周期重发；稳定 `SourceEventId` 和业务去重键避免重复业务效果。
5. 重复 ACK 幂等；未知 ID 不制造错误。
6. `InspectionFinishedEvent` 仅用于观测，不进入必须 ACK 的 Outbox。

运维处置：

- `ExportPendingEvents(offset, limit)` 分页导出当前未确认事件和一次性 `purgeToken`。
- `PurgeOutbox(confirmToken)` 仅在令牌与当前 Outbox 快照匹配时清空。
- 上述 Method 需要管理员权限并进入审计日志。

## 5. Outbox 与队列容量

- Outbox 默认硬上限 1000，高水位默认 800。
- 达到高水位时拒绝新开检；达到硬上限时拒绝检测和完工。
- SQLite 队列默认上限 100；队列满时拒绝新事件，不驱逐既有任务，也不 ACK Outbox。
- 容量拒绝通过 `/qc/status`、Prometheus 指标和告警暴露。
- 这使系统在压力下选择“明确拒绝 + 保留证据”，而不是“丢旧任务 + 假装成功”。

## 7. 明确边界

- **不是跨进程单事务**：状态+Outbox 原子提交，Node-RED 队列是下游幂等消费者。
- **不是 exactly-once**：MES 仍为 at-least-once + 接收端幂等。
- **不是零丢失存储**：SQLite 磁盘满、损坏、断电仍需要监控、备份和恢复演练。
- **不是多实例控制面**：Server 仍为单写者，没有多实例选主。
- **Edge Core 尚未完成物理收敛**：两边已共用 `delivery-record.schema.json` 读模型，并且 Edge Core 已有独立 UA 写回适配器；Node-RED 队列与 `edge_core/deliveries` 仍是两套物理表和发送泵。
- **Outbox 不自动压缩**：ACK 后删除，积压需要容量告警和受控清理。
