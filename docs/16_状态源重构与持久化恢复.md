# 状态源重构与持久化恢复

> 日期：2026-11-21 ｜ 当前证据：`.tmp/regression-20261121-005716/summary.json` ｜ 一键回归：29 个测试模块、496 项断言/用例通过

## 1. 本轮完成了什么

本轮完成的是“工位控制状态单写者 + 可恢复持久化”的垂直切片，不是整套 Edge Core 替换：

- `DeviceStatus`、`CurrentWorkOrderId`、`CurrentPartSN` 改为外部只读，只能由 Server 内受控状态迁移或检测入口更新。
- `StartInspection`、`CompleteWorkOrder`、`ResetCounters` 和 `record_inspection` 共用同一把进程内异步锁，避免检测结果与完工并发交错。
- 工单、计数器、滑动窗口、SN 日序列和最近检测结果写入版本化 JSON 快照。
- 服务启动时恢复快照；进程重启后不静默把工单、计数和 SN 归零。
- 新增真实 `SIGKILL` 重启测试，验证运行中工单、计数、SN 序列续增和完工能力。
- NG 与完工事件进入与工位快照同一文件的持久化 outbox；Node-RED 成功写入 SQLite 队列后才调用 `AcknowledgeEvent`，未确认事件会周期重发。
- 事件携带稳定的 `SourceEventId`、`CorrelationId` 和 `EventVersion`；重发保持同一业务身份，消费端按 NG 序列号/工单号做强幂等。
- outbox 增加高水位和硬上限：达到高水位时拒绝新开检，达到硬上限时拒绝新检测与完工，宁可返回明确拒绝也不静默删除 NG/完工业务事件。
- `QCStation.Events` 暴露只读的 `OutboxStatus` JSON、积压数、最老事件年龄、容量、高水位和背压标志；Node-RED 通过心跳读取并映射到 `/qc/status`、`/healthz` 和 `/metrics`。
- 新增管理员 Method：`ExportPendingEvents(offset, limit)` 分页导出并返回当前快照的清理令牌；`PurgeOutbox(confirmToken)` 只接受该令牌，空 outbox 清理幂等，匿名调用被拒绝。

MES 投递队列仍由 Node-RED 的 SQLite WAL 事务队列承载。它和 OPC UA Server 的控制状态目前是两个明确的持久化边界；本轮的成果是把工位状态从纯内存提升为可恢复状态，并未宣称两者已经收敛为同一事务。

## 2. 状态所有权

| 状态 | 当前权威来源 | 写入方式 | 恢复方式 |
|---|---|---|---|
| 设备状态、当前工单、目标数 | `QCStation` + `QC_STATE_PATH` 快照 | `StartInspection` / `CompleteWorkOrder` | 启动时读取快照 |
| 检测计数、OK/NG 数、滑动窗口 | `QCStation` + `QC_STATE_PATH` 快照 | `record_inspection` / `ResetCounters` | 启动时读取快照 |
| 当前 SN、SN 日序号 | `QCStation` + `QC_STATE_PATH` 快照 | Server 检测入口 | 启动时读取快照并继续递增 |
| NG/完工待确认事件 | `QCStation` + `QC_STATE_PATH` 快照中的 `outbox` | `record_inspection` / `CompleteWorkOrder` 入队，`AcknowledgeEvent` 删除 | 启动后重发至收到 ACK |
| outbox 积压与容量状态 | `QCStation` 内存状态 + UA `Events.OutboxStatus` | 入队、ACK、清空后同步只读变量 | 启动时由快照重新计算 |
| MES 队列、去重、死信、投递指标 | Node-RED SQLite WAL | Node-RED 事务 | SQLite 重启恢复 |
| MES 回执展示变量 | OPC UA 只读变量 | `RecordMesReceipt` 单写者 | Node-RED 队列恢复后继续调用 Method |
| 可视化编排与操作界面 | Node-RED | 操作员/受保护 HTTP | flow 文件与 SQLite 状态 |

三个 MES 回执变量 `LastMesOrderNo`、`LastNgMesOrderNo`、`LastCompletionReceiptNo` 也已收紧为外部只读。Node-RED 只能调用 `RecordMesReceipt`，由服务端在同一把状态锁内写具体变量与兼容镜像并读回确认；管理员直接写同样会被拒绝。当前 QCStation 业务变量全部只读，写入能力只存在于受控 Method 和内部检测入口。

## 3. 状态机规则

### 3.1 工单迁移

| 当前状态 | 输入 | 结果 |
|---|---|---|
| Idle | 非空 `workOrderId` 且 `targetCount > 0` | 进入 Running，绑定工单和目标数 |
| Running | 同一 `workOrderId` 再次 `StartInspection` | 幂等接受，状态不重置 |
| Running | 不同 `workOrderId` | 拒绝，不覆盖当前工单 |
| Fault | `StartInspection` | 拒绝 |
| Running | 正确的 `CompleteWorkOrder` | 发出完工事件，回到 Idle，清空工单与目标数 |
| 非 Running / 工单不一致 | `CompleteWorkOrder` | 拒绝，不修改状态 |
| 非 Running | `record_inspection` | 丢弃，并返回未接受 |
| 任意可开检状态且 outbox 达到高水位 | `StartInspection` | 拒绝，提示先 ACK 或受控清空积压 |
| Running 且 outbox 达到硬上限 | `record_inspection` / `CompleteWorkOrder` | 拒绝，状态和计数不部分提交 |

### 3.2 并发与一致性

- 所有会修改工位业务状态的入口先取得同一把 `asyncio.Lock`。
- 完工事件发出后，迟到的检测结果无法再挂到已结束工单。
- 每次状态变更与 outbox 入队先写入同一份快照，再同步 UA 变量和发布事件；持久化使用异步线程执行文件 `fsync`，避免阻塞 OPC UA 事件循环和订阅发布。
- 同一进程内是单写者；当前不支持多个 Server 进程同时写同一个状态文件。

### 3.3 事件 outbox 与 ACK

```text
受锁状态变更
  -> 同一快照写入 NG / 完工待确认事件
  -> fsync + 原子替换
  -> 周期发布待确认事件
  -> Node-RED 解析并写入 SQLite 队列
  -> 调用 QCStation.AcknowledgeEvent(eventId 或 correlationId)
  -> 从 outbox 删除并再次原子落盘
```

- `InspectionFinishedEvent` 仅用于观测，属于尽力发布；不进入 outbox，也不要求 ACK。
- NG 与完工事件在收到 ACK 前会按 `QC_OUTBOX_REPLAY_INTERVAL`（默认 2 秒）重复发布。
- 同一事件的重发使用相同 `SourceEventId`/`CorrelationId`；已经 ACK 的事件再次 ACK 返回成功，保持幂等。
- 崩溃可能发生在“发布成功、ACK 未落盘”之间，因此投递语义仍是 **at-least-once**，不是 exactly-once。

### 3.4 容量、背压与人工处置

```text
pending < highWatermark
  -> 正常运行
highWatermark <= pending < capacity
  -> OutboxBackpressure=true
  -> 拒绝新 StartInspection，已有工单可继续检测和完工
pending >= capacity
  -> 拒绝 record_inspection / CompleteWorkOrder
  -> 不丢弃事件、不部分更新计数，等待 ACK 或人工处置
```

- `QC_OUTBOX_MAX_PENDING` 默认 1000；`QC_OUTBOX_HIGH_WATERMARK` 默认 800，且始终收敛到 `1..capacity`。
- Node-RED 每 5 秒读取 `ns=2;s=QCStation.Events.OutboxStatus`。状态包含 `pendingCount`、`oldestAgeSeconds`、`capacity`、`highWatermark`、`backpressure`、最近 ACK/清空时间和拒绝次数；只要 outbox 非空，UA Server 会在每个重发周期刷新最老事件年龄，避免无新事件时年龄冻结。
- `/qc/status` 返回 `outbox` 对象；`/healthz` 在背压时返回 503 `degraded` / `OUTBOX_BACKPRESSURE`；`/metrics` 暴露 `qc_event_outbox_pending`、`qc_event_outbox_oldest_age_seconds`、`qc_event_outbox_capacity`、`qc_event_outbox_high_watermark`、`qc_event_outbox_backpressure` 和 `qc_event_outbox_status_age_seconds`。
- 运维处置顺序：先调用 `ExportPendingEvents(offset, limit)` 导出待确认事件并留存证据，再调用 `PurgeOutbox(confirmToken)`。令牌绑定当前事件 ID 列表，outbox 变化后旧令牌自动失效；只有管理员会话可以调用，所有调用进入审计日志。
- 人工清空是显式破坏性操作，不是自动降级路径；正常恢复应优先让 Node-RED 重新订阅、入队并 ACK。

### 3.5 SQLite 队列容量与 ACK 边界

- Node-RED 的 SQLite 队列上限保持 100 条；达到上限后拒绝新事件，不再驱逐最旧 PENDING 任务。
- 拒绝发生在去重键写入和队列插入之前，不产生半完成状态；新事件不写去重键，后续重放仍可正常入队。
- 只有事件已持久化到 SQLite（新入队或已存在的去重记录）时，Node-RED 才调用 `AcknowledgeEvent`。容量拒绝返回空消息，UA outbox 保留事件并按周期重试。
- `/qc/status` 暴露 `lastEnqueueRejection`；`qc_enqueue_total{outcome="rejected"}` 记录拒绝次数；`QcQueueEnqueueRejected` 在 5 分钟内出现拒绝时告警。
- 该策略仍不是跨 SQLite 与 UA 快照的分布式事务，但把边界收敛为：未得到 SQLite 持久确认的事件绝不 ACK。

## 4. 持久化格式与恢复语义

状态文件使用 `schemaVersion: 1`，包含：

- 工单与设备状态；
- 目标数、检测总数、OK/NG 数；
- 最近滑动窗口；
- 当前 SN、SN 日期和序号；
- 最近结果、缺陷、置信度、图像号和时间戳。
- 待确认 NG/完工事件 outbox（`eventVersion=1`，含稳定事件 ID、关联 ID、字段、严重级别和消息）。

写入流程：

```text
构造不可变快照
  -> 写同目录临时文件
  -> flush + fsync
  -> os.replace 原子替换
  -> fsync 父目录（尽力而为）
```

恢复规则：

- 文件不存在：使用默认 Idle 状态。
- JSON 损坏或 schema 不兼容：记录告警并回退默认状态，不中断服务启动。
- Running 状态缺少工单：回退 Idle，避免无法完工的悬挂状态。
- 计数和窗口做边界清洗；置信度限制在 0–1。

`SIGKILL` 恢复测试验证了：

1. 崩溃前处于 Running 的工单和计数可以从快照恢复；
2. 服务重启后仍能识别当前工单；
3. 新 SN 从持久化序号继续递增，而不是回到 `000001`；
4. 恢复后的工单可以调用 `CompleteWorkOrder` 回到 Idle。

事件 outbox 恢复测试验证了：

1. 未 ACK 的 NG 事件在 `SIGKILL` 后仍保留在快照中；
2. 重启后事件可以重新送达订阅者，并保留 `SourceEventId`、`CorrelationId`、工单和 SN；
3. 重复发布使用同一稳定事件 ID；
4. ACK 后事件从磁盘快照移除，重复 ACK 幂等，之后不再重发。
5. 积压计数和背压状态在 `SIGKILL` 后从快照恢复；高水位下新开检被拒绝，ACK 排空后恢复；
6. 匿名导出/清空被拒绝，错误或过期令牌不会删除事件，正确令牌清空后落盘且再次清空幂等。

## 6. 明确边界

- **不是零数据丢失**：状态与 outbox 在同一快照内落盘，但 UA Server 快照与 Node-RED SQLite 仍是两个事务边界；ACK 前崩溃会产生重复投递，而不是静默丢失。
- **不是 exactly-once 事件总线**：ACK 后仍可能有一份已在网络上飞行的重复事件；消费端必须按 `SourceEventId`/`CorrelationId` 或业务指纹幂等。
- **outbox 已有界但仍是单文件快照**：超过高水位会拒绝新开检，超过硬上限会拒绝检测/完工；不会静默删除业务事件。人工清空是带令牌的审计操作，没有自动压缩、事件合并或按磁盘剩余空间动态调整容量的能力。
- **还没有磁盘满实测**：容量控制能限制业务积压，但不能替代磁盘配额、WAL/状态文件体积告警和真实的只读/满盘故障演练。
- **不是多进程安全**：锁只覆盖单进程；多 Server 实例同时写同一文件会产生覆盖风险。
- **不是 Edge Core 已替换 Node-RED**：外部 Edge Core 垂直切片和在线 Node-RED 队列仍并存，尚未统一为一个控制面。
- **不是 exactly-once**：MES 投递仍是 at-least-once + 接收端幂等，必须保留这一合同口径。
- **不是生产级存储方案**：JSON 快照适合单工位试点与恢复基线，不适合多工位、多租户或高并发写入。

## 7. 后续计划

1. 把工位控制状态、事件 outbox 与队列状态收敛到同一个 SQLite 事务边界，优先统一 `workOrderId + correlationId + deliveryId + sourceEventId` 的关联关系。
2. 明确零检测完工、超额检测、重复工单 `attemptId` 和目标数到达后的状态语义。
3. 增加磁盘满、权限错误、状态文件回滚和备份恢复演练，并测试 outbox 接近磁盘上限时的降级行为。
4. 把 Node-RED 在线发送泵迁移到 Edge Core 适配器，Node-RED 只保留编排和操作界面。
5. 在真实 MES 沙箱和现场负载下复验恢复时间、回执对账率和状态一致性。
