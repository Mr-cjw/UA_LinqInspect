# 项目总览与现场演示：AI 看见缺陷，交付不让结果丢失

> 用途：项目介绍、现场演示、技术复核和试点沟通。页面展示的是可运行的软件证据，不是生产验收报告。AI 推理、合成数据边界、可靠交付和模拟 MES 必须一起说明。

## 1. 项目一句话

AI 质检先发现缺陷；但看见 NG 只是入口。真正难的是让这条记录可靠进入 MES，并在 MES 超时、断网或服务重启后仍能对账；设备停机和温度异常发生时，还要能解释质量损失与设备上下文之间的关系。

项目由四部分组成：

1. **AI 质检入口**：先做图像质量门禁，再由本地视觉模型真实推理，输出缺陷类别、置信度、概率分布、类别级指标和模型卡；图像质量不合格或低置信度的 OK/NG 都转人工复核；
2. **Node-RED 工作流**：保留现场编排、接口衔接和快速接入能力，已有流程继续回归，不推倒重来；
3. **Edge Core 质量交付主线**：用 SQLite Outbox、Worker 和状态机承接可靠投递、重试、死信、重放与审计；
4. **设备上下文项目**：从 Mock PLC 的 OPC UA Server 采集状态、产量、温度和报警，补上 OEE 分解与 RCA 候选。

四个部分不是互相替代，而是从“看见缺陷”到“接得进来”，再到“交付可靠”和“损失可解释”。

## 2. 现场打开什么

```bash
cd ~/project_files/UA_LinqInspect
.venv/bin/python scripts/demo_edge_core.py --ui --no-open
```

浏览器打开：

```text
http://127.0.0.1:8899/overview
```

先打开 AI 质检真实推理页：

```text
http://127.0.0.1:8899/vision
```

选择 `划痕 / 凹坑 / 污渍 / 缺件 / 正常` 任一内置样本，页面会先检查图像质量，再运行本地模型并显示类别、置信度、概率分布、模型版本和推理/门禁处理耗时。只有图像质量合格且判定为 NG 才能点击“送入质量闭环”。

再回到总览页点击“现场运行演示”。页面约 20 秒完成一次联合场景：

```text
本地视觉推理
  → 图像质量门禁
  → 缺陷类别与置信度
  → 置信度门禁
设备停机与温度异常
  → 一条质检 NG
  → SQLite / Edge Core 投递
  → 故障、重试与死信
  → 服务重启与人工重放
  → MES 回执与 UA 写回
  → OEE 分解
  → RCA 候选原因
```

每次运行都会生成新的 `deliveryId`、`correlationId`、MES 回执号和审计时间线，不是预录动画。

AI 推理也是真实执行：第一次运行会在本机训练 850 张合成样本，之后对图像做前向推理。训练和验证数据均为程序合成，留出集准确率、宏平均召回率和类别级指标只对合成数据成立，不是客户现场精度。

## 3. 一条 NG 的价值链路

### 没有这套系统

- NG 靠人工登记，MES 超时或断网后容易漏单；
- 重复上报可能重复开单，月底只能靠 Excel 对账；
- 设备停机、温度异常与质量结果分散在不同系统，无法形成证据链；
- 每个客户重复开发接口，项目做完仍难复制。

### 有这套系统

- AI 先输出缺陷类别、置信度和概率分布，低置信度的 OK/NG 都不自动放行或开单；
- 业务事件先进入本地事务队列，MES 不在线也不会静默丢失；
- 同一业务键幂等，重试失败进入可见死信，人工重放保留原回执和审计；
- 只有 MES 回执与 OPC UA 写回都确认，交付才进入 `DONE`；
- 同一时间窗下钻到 OEE 的 A/P/Q，并把设备异常列为有证据的 RCA 候选。

## 4. 今天演示真正证明了什么

| 结论 | 现场证据 | 当前含义 |
|---|---|---|
| AI 质检链路真实可运行 | 图像质量门禁、本地模型训练、图像推理、概率输出、类别级模型卡、模型/图像哈希和置信度门禁 | 证明推理与决策链路可跑，不等于生产精度 |
| 质检结果不会因 MES 故障静默消失 | SQLite Outbox、重试、死信与重放 | 可靠性有可验收的软件底座 |
| 重复上报不会重复形成业务结果 | 业务键幂等与回执校验 | 降低重复开单和对账风险 |
| 服务重启后还能继续 | 真实重建服务并恢复持久化任务 | 现场运维风险可被观察和控制 |
| 业务结果和设备上下文能对齐 | 两个仓库联合运行，共享工单、SN 与时间窗 | 可继续验证 OEE/RCA 增值能力 |
| 结果不是预录动画 | 每次生成新的业务编号、回执和状态轨迹 | 可在现场重复运行和复核 |

## 5. 真实运行与模拟边界

| 环节 | 当前状态 | 说明 |
|---|---|---|
| 本地视觉推理 | 真实运行 | NumPy 小型 MLP，对上传或内置图片执行真实前向推理 |
| 图像质量门禁 | 真实运行 | 分辨率、亮度、对比度、清晰度和过曝/欠曝不合格时转人工复核，不执行自动分类 |
| 视觉训练/验证图像 | 程序合成 | 不代表真实工厂图像分布 |
| 视觉留出集指标 | 准确率、宏平均召回率与类别级 Precision/Recall，仅对合成数据成立 | 不是客户现场精度，也不代表未知缺陷零漏检 |
| 置信度门禁 | 真实运行 | 低于阈值只转人工复核，不自动开单 |
| Edge Core API | 真实运行 | 项目内实际 API、状态查询和审计数据 |
| SQLite Outbox | 真实运行 | 本地事务写入、重试、死信与重放 |
| Worker / 状态机 | 真实运行 | 发送泵、状态迁移和重启恢复逻辑 |
| Mock PLC OPC UA Server | 真实运行 | 同级设备上下文项目中的可运行模拟器 |
| 设备故障注入与变量读取 | 真实运行 | 通过 OPC UA Method 和订阅完成 |
| 下游 MES | 本地模拟 | 不冒充客户 MES |
| OPC UA 回执写回 | 本地模拟 | 不冒充生产写回链路 |
| 客户真实 PLC / 产线网络 | 尚未接入 | 需要现场点位清单、网络和安全评审 |
| 长期稳定性与实施人天 | 尚未验证 | 需要在付费试点中测量 |

明确边界：

- 当前是可运行的软件先行 PoC+，**不是生产集成**；
- 视觉模型是合成数据 Demo，**不是生产视觉验收**；未知缺陷可能被归入最相似的已知类别；
- 图像质量门禁只拦截明显不可用输入，**不能替代真实相机、光源、工装和采图验收**；
- 概率未做现场校准，高置信度不等于真实产线正确率；
- 不承诺 exactly-once，采用 at-least-once 加业务幂等；
- RCA 只表示时间相关性和候选原因，不是因果证明；
- 真实 PLC、客户 MES、生产网络、长期稳定性和商业付费意愿仍需试点验证。

## 6. 四层能力与落地顺序

| 层次 | 解决什么 | 试点必须证明 |
|---|---|---|
| AI 质检入口 | 输出缺陷类别、置信度与概率分布 | 客户样本、真实相机条件、漏检/误检、未知缺陷策略、低置信度复核 |
| 质量连接器 | 质检结果可靠进入 MES，回执可对账 | 幂等、超时重试、死信重放、重启恢复、MES 沙箱验收 |
| 设备上下文包 | 采集 PLC 状态、产量、温度、报警 | 点位清单、采样频率、断线边界、质量事件与设备快照对齐 |
| OEE / RCA 增值层 | 分解损失并给出候选原因 | OEE 数字可下钻、RCA 证据可追溯、工程人员认可有帮助 |

扩张顺序固定：单工位 → 多工位 → 单产线 → 多工厂；单 MES → 适配器库；视觉入口 → 连接器 → 设备上下文 → 分析增值。

## 7. 90 天落地计划

### 第 1–2 周：锁定边界

确定一个产品族、一组客户样本、一种工单、一套 MES 接口和一个 PLC 只读点位集。交付“单工位试点范围、样本与点位清单”。

### 第 3–6 周：视觉与 MES 沙箱验收

验证真实样本上的漏检/误检、置信度门禁、幂等合同、故障恢复、回执对账、重试和 RTO。交付“视觉与 MES 沙箱验收报告”。

### 第 7–9 周：标准化沉淀

沉淀模型版本、部署包、监控、备份恢复、验收脚本和故障演练手册。交付“标准部署包与故障演练记录”。

### 第 10–12 周：独立复制

在第二个独立现场或渠道伙伴处验证，不以同一客户定制冒充复制。交付“第二现场验证报告”。

阶段门槛：

- 第 6 周拿不到真实样本验收、真实 MES 沙箱和可复验的故障恢复数据，就停止扩大范围；
- 试点没有明确付费意愿，就不把技术演示当成商业验证；
- 交付人天无法收敛、适配器不能复用，就不承诺跨客户快速复制。

## 8. 现场演示检查清单

1. 打开 `/vision`，选择一个 NG 样本，确认模型输出类别、置信度和概率分布；
2. 打开模型卡，确认图像质量门禁、合成数据、非生产精度和低置信度转人工边界可见；
3. 打开 `/overview`，点击“现场运行演示”，观察 AI 推理、设备异常、NG 投递、失败重试、死信、重启恢复和最终回执；
4. 确认结果为 `DONE`，MES 回执形如 `MES-JX-DEMO-0001`；
5. 确认 OEE 在 0–1 之间，A/P/Q 三个因子有来源；
6. 打开 `/joint` 查看更细的联合时间线和审计轨迹；
7. 主动说明视觉数据合成、Mock PLC、模拟 MES 和未接入生产网络的事实。

如果运行失败，先检查：

- 同级 `rpi4-opcua-oee-rca-gateway` 仓库是否存在；
- 该仓库是否执行过 `npm install`；
- Python 环境是否安装 `numpy` 和 `Pillow`；
- `node` 是否可执行；
- 8899 端口是否已有旧演示服务占用；
- 终端是否有 Mock PLC 或 OPC UA 连接错误。

## 9. 项目当前需要回答的三个问题

1. **问题是否真实存在？** NG 进入 MES 时是否真的会漏单、重复开单或依赖人工对账？客户是否愿意为可靠性付费？
2. **运行证据是否可复现？** 能否在客户设备上主动制造超时、断网和重启，并展示同一业务键、回执与审计记录？
3. **是否具备标准复制路径？** 单站实施能否控制在有限人天，适配器能否复用，第二个独立现场能否重复验收？
