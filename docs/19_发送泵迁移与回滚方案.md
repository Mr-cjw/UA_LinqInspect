# 发送泵迁移与回滚方案

> 日期：2026-11-21 ｜ 目标：把 Node-RED 在线队列迁移到 Edge Core 单一权威发送泵
>
> 结论：产品方向选择 **Edge Core 作为权威投递状态和发送泵**，Node-RED 保留事件接入、可视化和人工操作。UA 写回适配器、新事件直写、跨进程发送权互锁、真实 Node-RED 在线流量切换、MES HTTP Basic 和回滚准备已经完成；真实 MES 沙箱、工厂网络和现场回滚仍需单独验证。当前不能宣称已完成生产接管。

## 1. 为什么需要迁移

当前两条在线/垂直链路：

- Node-RED 使用 `queue + ua_writebacks + ua_write_targets` 完成 MES 发送和 UA 回执写回；
- Edge Core 使用 `deliveries + delivery_events + dead_letters` 完成状态机、重试、死信和外部 API。

两边已经共用 `contracts/delivery-record.schema.json` 读模型，但物理表和发送泵仍不同。继续长期并存会带来：

- 同一事件可能在两边各入队一次；
- 两个发送泵同时运行会重复调用 MES；
- 查询、对账、死信重放和备份需要维护两套口径；
- 产品对外承诺的权威状态不明确。

因此目标只能是**一个事件最多进入一个权威发送泵**。

## 2. 权威边界决策

| 能力 | 目标归属 |
|---|---|
| 质检事件接入 | Edge Core API 或 Node-RED 适配后调用 Edge Core API |
| 投递、重试、死信、租约 | Edge Core SQLite |
| MES 调用与回执校验 | Edge Core Worker |
| OPC UA 回执写回 | 独立 UA Writeback Adapter |
| 可视化编排、人工操作 | Node-RED |
| 工单和检测状态 | OPC UA Server |

迁移过程中禁止：

- 同时启动 Node-RED 发送泵和 Edge Core Worker 处理同一批任务；
- 在 Node-RED 已发送成功但尚未写入 Edge Core 时 ACK UA Outbox；
- 用 `-X theirs` 或覆盖式 SQL 迁移解决未知冲突。

## 3. 已实现的迁移工具

工具：

```text
scripts/migrate_nodered_to_edge_core.py
```

默认只做 dry-run：

```bash
.venv/bin/python scripts/migrate_nodered_to_edge_core.py \
  --source data/qc-queue.sqlite \
  --target data/edge_core.sqlite3
```

确认摘要后再应用：

```bash
.venv/bin/python scripts/migrate_nodered_to_edge_core.py \
  --source data/qc-queue.sqlite \
  --target data/edge_core.sqlite3 \
  --apply
```

迁移工具当前保证：

- 源库与目标库必须是不同文件；
- 校验 Node-RED 表结构、列和 `integrity_check`；
- dry-run 不创建目标库；
- 同一源库重复执行幂等；
- 同业务键不同 payload 返回冲突，不覆盖目标；
- 保留 Node-RED queue ID 作为 `businessKey`；
- 生成确定性的 UUID `deliveryId`；
- `PENDING/SENDING` 导入为 Edge Core `PENDING` 或 `UA_WRITE_PENDING`；
- 死信导入为 `DEAD` 并保留错误码、原因和失败时间；
- 已存在 MES 回执的 UA 写回任务保留规范化回执；
- 为旧 Node-RED payload 补齐 `schemaVersion/sourceEventId/stationId/eventType/correlationId`，NG 事件补齐 `result=NG`，保证 Edge Core Worker 能按事件类型校验 MES 回执；
- 写入 `delivery_events` 迁移审计。

> 2026-11-21 修复：迁移测试发现旧队列 payload 没有 `eventType`，Edge Core Worker 即使收到合法 MES 回执也会按 `INVALID_EVENT_TYPE` 进入死信。迁移器现在统一补齐规范事件信封，并由切换演练覆盖真实 Worker 发送和回执校验。

## 4. 切换步骤

### 阶段 A：预检

1. 停止 Node-RED 发送泵或进入只读维护模式。
2. 等待在途 MES 请求结束，记录 `/qc/status`。
3. 备份 Node-RED 队列和 Edge Core 数据库。
4. 执行迁移脚本 dry-run。
5. 检查 `conflicts` 必须为空。

### 阶段 B：离线导入

1. 执行 `--apply`。
2. 比较源队列、死信和回执数量与迁移摘要。
3. 启动 Edge Core API/Worker，确认队列开始按预期推进。
4. 禁止重新启动 Node-RED 发送泵。

### 阶段 C：UA 写回

Edge Core 收到 MES 回执后停在 `UA_WRITE_PENDING`，由独立适配器完成：

1. 查询待写回任务；
2. 从 `mesReceipt` 读取 `receiptType/receiptNo/correlationId`；
3. 调用 OPC UA `RecordMesReceipt`；
4. 校验返回值；
5. 调用 `POST /v1/deliveries/{id}/ua-write-result` 推进 `DONE`。

适配器已实现并通过真实安全 OPC UA 集成测试，且已在 `QC_DELIVERY_AUTHORITY=edge-core` 时纳入 systemd 条件启动。它仍需要在完整切换演练中与真实 UA Server 和真实 MES 串成一条链路。

### 阶段 D：新事件接入

Node-RED 的 NG/完工事件入队函数已经支持直写 Edge Core `POST /v1/inspection-events`：

- 只有 API 返回 202 或幂等命中后才 ACK UA Outbox；
- `QC_DELIVERY_AUTHORITY=edge-core` 时禁止同时写 Node-RED 本地队列；
- Node-RED 不再执行本地发送泵；
- Edge Core 返回 503/超时时不 ACK，由 UA Outbox 重发。

## 5. 回滚条件

出现以下任一情况应回滚：

- 迁移冲突无法人工解释；
- 导入后计数不一致；
- Edge Core 连续拒绝合法事件；
- MES 请求数异常翻倍；
- UA 写回适配器无法确认；
- 死信不可重放。

回滚步骤：

1. 停止 Edge Core Worker；
2. 保留 Edge Core 数据库和迁移日志；
3. 恢复 Node-RED 队列备份；
4. 重新启动且只启动 Node-RED 单一发送泵；
5. 用 MES 幂等记录核查切换窗口是否产生重复业务单。

## 6. 跨进程单发送权

Node-RED 和 Edge Core 共享同一个租约目录。实现上先写完整的临时目录，再通过一次原子重命名发布锁；Python 与 Node.js 双方读取同一份 `owner.json`，并校验 PID、心跳、token 和目录 inode。

已覆盖：

- Node-RED 持有租约时，Edge Core 进程以退出码 3 拒绝启动；
- Edge Core 退出后 Node-RED 可以重新获得发送权；
- 4 轮、每轮 4 个 Node 进程与 4 个 Python 进程并发争抢，始终只有一个赢家；
- 进程异常退出后，过期租约可由另一方恢复。

该机制只保证本地单机只启动一个发送泵，不替代 MES 接收端幂等，也不支持多 Edge Core 实例的分布式选主。

## 7. 受控实验室切换/回滚演练

自动化入口：

```bash
.venv/bin/python tests/sender_cutover_test.py
```

演练覆盖：

1. Node-RED 持有发送权，真实 Edge Core 进程拒绝启动；
2. 离线 dry-run 和 apply 将 2 条 Node-RED 队列任务迁入 Edge Core；
3. Node-RED 释放租约后，Edge Core 进程接管，并确认锁文件 PID 为 Edge Core；
4. Edge Core Worker 调用本地假 MES，收到 NG 单号和完工回执；
5. 任务进入 `UA_WRITE_PENDING`，通过 API 回报 UA 写回成功后进入 `DONE`；
6. Edge Core 正常退出并释放租约，Node-RED 重新获得发送权；
7. Node-RED 源库对象数保持不变，仍可作为回滚数据源；
8. 重复执行迁移保持幂等，不产生第二条投递记录。

本次证据：**sender_cutover 1/1 PASS**。该演练验证的是控制面、迁移、Worker、回执校验和回滚准备，不等同于真实工厂切换。

## 8. Node-RED 在线全链路切换演练

自动化入口：

```bash
.venv/bin/python tests/edge_core_online_flow_test.py
```

该演练启动隔离的 UA Server、Node-RED、Edge Core、MES 模拟端点和真实 UA 写回适配器，覆盖：

1. Node-RED 在 `node-red` 权威模式下先持有发送权；
2. 停止 Node-RED 后 Edge Core 接管租约，Node-RED 本地发送泵被互锁；
3. Node-RED 以 `edge-core` 权威模式启动，继续订阅 UA 事件；
4. 真实 UA 工单产生 8 条 NG 和 1 条完工事件；
5. Node-RED 直写 Edge Core，Edge Core Worker 通过 HTTP Basic 调用受保护的 MES 端点；
6. 9 条投递全部获得合法回执，真实 UA 写回适配器调用 `RecordMesReceipt`；
7. 所有投递进入 `DONE`，Edge Core 队列和死信为空；
8. Node-RED 在 Edge Core 接受事件后才 ACK UA outbox，积压最终归零；
9. UA `LastNgMesOrderNo`、`LastCompletionReceiptNo` 与 Edge Core 回执一致；
10. 停止 Edge Core 后 Node-RED 重新获得发送权，Edge Core 审计库仍保留 9 条 `DONE` 记录。

本次证据：**online_cutover 14/14 PASS**。与上一节的区别是，本节已经跑通真实 Node-RED 入口、Edge Core、MES 鉴权回执和真实 UA Method 写回，不再只是手工回报 UA 成功。

仍未覆盖：真实 MES 厂商 SDK/字段差异、真实工厂网络切换、现场证书与账户、长时间运行和跨实例 HA。
