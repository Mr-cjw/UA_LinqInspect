# 发送泵迁移与回滚方案

> 日期：2026-11-21 ｜ 目标：把 Node-RED 在线队列迁移到 Edge Core 单一权威发送泵
>
> 结论：产品方向选择 **Edge Core 作为权威投递状态和发送泵**，Node-RED 保留事件接入、可视化和人工操作。UA 写回适配器已经实现并通过真实安全 OPC UA 集成测试；当前仍是分阶段迁移，不是双写，新事件直写和双泵互锁未完成前不能直接切换生产流量。

## 1. 为什么需要迁移

当前两条在线/垂直链路：

- Node-RED 使用 `queue + ua_writebacks + ua_write_targets` 完成 MES 发送和 UA 回执写回；
- Edge Core 使用 `deliveries + delivery_events + dead_letters` 完成状态机、重试、死信和外部 API。

两边已经共用 `contracts/delivery-record.schema.json` 读模型，但物理表和发送泵仍不同。继续长期并存会带来：

- 同一事件可能在两边各入队一次；
- 两个发送泵同时运行会重复调用 MES；
- 查询、对账、死信重放和备份需要维护两套口径；
- 产品对外承诺的权威状态不明确。

因此目标只能是**一个事件最多进入一个权威发送泵**。

## 2. 权威边界决策

| 能力 | 目标归属 |
|---|---|
| 质检事件接入 | Edge Core API 或 Node-RED 适配后调用 Edge Core API |
| 投递、重试、死信、租约 | Edge Core SQLite |
| MES 调用与回执校验 | Edge Core Worker |
| OPC UA 回执写回 | 独立 UA Writeback Adapter |
| 可视化编排、人工操作 | Node-RED |
| 工单和检测状态 | OPC UA Server |

迁移过程中禁止：

- 同时启动 Node-RED 发送泵和 Edge Core Worker 处理同一批任务；
- 在 Node-RED 已发送成功但尚未写入 Edge Core 时 ACK UA Outbox；
- 用 `-X theirs` 或覆盖式 SQL 迁移解决未知冲突。

## 3. 已实现的迁移工具

工具：

```text
scripts/migrate_nodered_to_edge_core.py
```

默认只做 dry-run：

```bash
.venv/bin/python scripts/migrate_nodered_to_edge_core.py \
  --source data/qc-queue.sqlite \
  --target data/edge_core.sqlite3
```

确认摘要后再应用：

```bash
.venv/bin/python scripts/migrate_nodered_to_edge_core.py \
  --source data/qc-queue.sqlite \
  --target data/edge_core.sqlite3 \
  --apply
```

迁移工具当前保证：

- 源库与目标库必须是不同文件；
- 校验 Node-RED 表结构、列和 `integrity_check`；
- dry-run 不创建目标库；
- 同一源库重复执行幂等；
- 同业务键不同 payload 返回冲突，不覆盖目标；
- 保留 Node-RED queue ID 作为 `businessKey`；
- 生成确定性的 UUID `deliveryId`；
- `PENDING/SENDING` 导入为 Edge Core `PENDING` 或 `UA_WRITE_PENDING`；
- 死信导入为 `DEAD` 并保留错误码、原因和失败时间；
- 已存在 MES 回执的 UA 写回任务保留规范化回执；
- 写入 `delivery_events` 迁移审计。

## 4. 切换步骤

### 阶段 A：预检

1. 停止 Node-RED 发送泵或进入只读维护模式。
2. 等待在途 MES 请求结束，记录 `/qc/status`。
3. 备份 Node-RED 队列和 Edge Core 数据库。
4. 执行迁移脚本 dry-run。
5. 检查 `conflicts` 必须为空。

### 阶段 B：离线导入

1. 执行 `--apply`。
2. 比较源队列、死信和回执数量与迁移摘要。
3. 启动 Edge Core API/Worker，确认队列开始按预期推进。
4. 禁止重新启动 Node-RED 发送泵。

### 阶段 C：UA 写回

Edge Core 收到 MES 回执后停在 `UA_WRITE_PENDING`，由独立适配器完成：

1. 查询待写回任务；
2. 从 `mesReceipt` 读取 `receiptType/receiptNo/correlationId`；
3. 调用 OPC UA `RecordMesReceipt`；
4. 校验返回值；
5. 调用 `POST /v1/deliveries/{id}/ua-write-result` 推进 `DONE`。

适配器已实现并通过真实安全 OPC UA 集成测试，但尚未自动纳入 systemd，也尚未完成新事件直写和双泵互锁；因此仍不能宣称发送泵切换已经达到生产可用。

### 阶段 D：新事件接入

将 Node-RED 的 NG/完工事件入队函数改为调用 Edge Core `POST /v1/inspection-events`：

- 只有 API 返回 202 或幂等命中后才 ACK UA Outbox；
- 禁止同时写 Node-RED 本地队列；
- Node-RED 不再执行本地发送泵；
- Edge Core 返回 503/超时时不 ACK，由 UA Outbox 重发。

## 5. 回滚条件

出现以下任一情况应回滚：

- 迁移冲突无法人工解释；
- 导入后计数不一致；
- Edge Core 连续拒绝合法事件；
- MES 请求数异常翻倍；
- UA 写回适配器无法确认；
- 死信不可重放。

回滚步骤：

1. 停止 Edge Core Worker；
2. 保留 Edge Core 数据库和迁移日志；
3. 恢复 Node-RED 队列备份；
4. 重新启动且只启动 Node-RED 单一发送泵；
5. 用 MES 幂等记录核查切换窗口是否产生重复业务单。

## 6. 当前完成度

已完成：

- 共享投递读模型；
- Node-RED 队列到 Edge Core 的离线、幂等、冲突检测导入工具；
- 迁移 dry-run/apply、状态映射、回执保留和死信保留测试（5/5 PASS）；
- 独立安全 OPC UA 回执写回适配器与真实 Method 集成测试（3/3 PASS）。

尚未完成：

- Node-RED 新事件直写 Edge Core API；
- Edge Core OPC UA 回执写回适配器的 systemd 部署与专用重试策略；
- 在线切换编排和双泵互锁；
- 真实 MES 沙箱切换演练；
- 工厂现场回滚演练。

在这些完成前，现有在线主链路仍以 Node-RED 发送泵为准；Edge Core 迁移工具属于切换准备，不应被描述为已完成生产接管。
