# 产品扩展路线与 MES 契约体检

> 日期：2026-11-21 ｜ 核心判断：扩展必须沿着“质检结果进入 MES 并形成可追溯业务闭环”这条数据链展开，不能靠随机加功能。

## 1. 为什么核心功能需要配套能力

当前核心连接器解决的是：

- 质检结果标准化；
- SQLite Outbox；
- 断网、超时、重试和重启恢复；
- MES 回执校验；
- 死信重放；
- OPC UA 回执写回；
- correlationId 对账。

但只有这些能力时，客户仍然会遇到四个落地问题：

1. 现场不知道怎么接、接得对不对；
2. MES 接口是否符合契约、是否幂等，没有快速判断工具；
3. 工厂操作员不会使用 Node-RED，也不应该直接操作编辑器；
4. 质量结果进入 MES 后，缺少证据链、异常处置和班次对账。

所以产品扩展不应平均用力，而应优先增加能同时改善**可用性、交付效率、销售证明和客户价值**的能力。

## 2. 最事半功倍的组合

### 2.1 核心连接器 + MES 契约体检工具

这是当前最先落地的配套能力。

价值：

- 在项目开始前先判断客户 MES 能不能接；
- 快速验证成功回执、重复请求、业务键冲突和非法请求行为；
- 把“接口问题”和“我们的连接器问题”提前分开；
- 减少现场联调人天；
- 输出可交付报告，适合付费诊断和售前验证；
- MES 厂商可以用它做适配器自检和版本回归；
- 集成商可以用它做项目预检，降低返工。

这不是又一个内部测试脚本，而是可以进入售前、诊断和交付流程的产品工具。

当前实现：

```text
scripts/mes_contract_doctor.py
```

### 2.2 核心连接器 + 本地操作台（MVP 已落地）

Node-RED 适合编排和排障，不适合作为最终操作员界面。产品需要一个轻量本地操作台：

- 工位状态；
- 当前工单；
- 扫码或手工输入 SN；
- 开始检测、完工；
- NG 待处置列表；
- 队列积压和死信；
- MES 最近回执；
- 一键重放和确认；
- 证书、磁盘、MES 延迟和 UA 连接健康。

只做本地 Web 页面即可，不需要复杂前端平台。目标是让工厂班组长不打开 Node-RED 也能完成日常工作。

这是把“技术上能用”变成“客户敢用”的关键一步。

### 2.3 核心连接器 + 质量证据包

每次 NG 或完工应能形成可追溯证据包：

- SN、工单、工位；
- 质检结果、缺陷类型和置信度；
- 图片或图片路径；
- 模型版本、阈值和推理时间；
- 来源事件 ID；
- MES 请求、回执号和时间；
- UA 写回确认；
- 异常、重试和人工处置记录。

通过 `correlationId` 一次查询即可还原完整链路。

这解决的是审计、客诉、质量追溯和“到底是谁的问题”的痛点。它也可以把视觉模块和连接器真正连接起来，而不是两个孤立产品。

### 2.4 核心连接器 + PLC/IO/扫码接入

很多工厂没有 OPC UA 质检结果，但有：

- 光电/接近开关；
- PLC 的 OK/NG 输出；
- 扫码枪；
- 老式串口或 TCP 设备；
- 文件、CSV 或数据库落地结果。

优先补一个轻量离散 IO 适配器：

- 扫码绑定工单和 SN；
- 读取 OK/NG 电平或脉冲；
- 防抖和边沿触发；
- 本地时间戳；
- 断线状态；
- 将结果转为标准事件。

这比增加很多 MES 专属页面更能扩大工厂覆盖面，因为大量存量设备仍是非 OPC UA 的。

### 2.5 核心连接器 + 返修/复检闭环

当前的 NG 事件只形成 MES 开单，但真实质量流程还包括：

- NG 品隔离；
- 返修或报废；
- 复检；
- 复检通过后关闭 NG；
- 返修记录和责任人；
- 最终良率与处置结果。

建议在本地操作台稳定后，再增加“返修/复检”闭环。它可以明显提高现场价值，但不应早于操作台和证据链。

## 3. 扩展优先级

| 组合 | 客户价值 | 复用性 | 开发难度 | 销售证明 | 结论 |
|---|---|---:|---:|---:|---|
| MES 契约体检 | 提前发现接口风险，减少联调 | 高 | 低 | 强 | 立即做，已完成首版 |
| 本地操作台 | 操作员能独立使用，降低交付依赖 | 高 | 中 | 强 | MVP 已落地 |
| 质量证据包 | 审计、客诉、根因和责任边界 | 高 | 中 | 强 | MVP 已落地 |
| PLC/IO + 扫码 | 接入大量非 OPC UA 存量设备 | 高 | 中高 | 强 | 第二优先级 |
| MES 适配模板库 | 降低重复接口开发 | 很高 | 中 | 很强 | 有 2～3 个真实接口后做 |
| 返修/复检闭环 | 更完整质量流程 | 中高 | 中高 | 中强 | 操作台稳定后做 |
| 多工位看板 | 扩站和产线管理 | 中高 | 中 | 中 | 有扩站客户后做 |
| YOLO 模型管理 | 视觉增值 | 中 | 高 | 依赖场景 | 保持可选，不挤占主线 |
| OEE/硬件 | 后置增值 | 低 | 高 | 弱 | 继续冻结 |

## 4. 当前新增：MES 契约体检工具

### 4.1 它检查什么

当前首版检查 7 个场景：

1. NG 开单首次请求是否返回合法同步回执；
2. 相同幂等键重复请求是否返回同一回执；
3. 同一 SN/工单携带不同缺陷时是否拒绝冲突；
4. 完工报工首次请求是否返回合法回执；
5. 完工重复请求是否返回同一回执；
6. 同一工单不同统计是否拒绝冲突；
7. 非法 NG 请求是否被拒绝。

### 4.2 输出

工具生成：

```text
report.json
report.md
```

包含：

- MES 地址与鉴权模式；
- 测试工单和 SN；
- 每个场景的 HTTP 状态；
- 回执号；
- 稳定错误码；
- `PASS/WARN/FAIL/DRY_RUN` 结论；
- 现场处置建议。

### 4.3 使用方式

默认 dry-run，不访问 MES：

```bash
.venv/bin/python scripts/mes_contract_doctor.py \
  --base-url http://127.0.0.1:1880 \
  --work-order WO-MES-DOCTOR-20261121 \
  --serial SN-MES-DOCTOR-20261121
```

真实执行必须显式确认写入：

```bash
.venv/bin/python scripts/mes_contract_doctor.py \
  --base-url http://mes-test.example.local \
  --work-order WO-MES-DOCTOR-20261121 \
  --serial SN-MES-DOCTOR-20261121 \
  --bearer-token "$MES_TOKEN" \
  --execute \
  --confirm-write WO-MES-DOCTOR-20261121
```

HTTP Basic：

```bash
.venv/bin/python scripts/mes_contract_doctor.py \
  --base-url http://mes-test.example.local \
  --work-order WO-MES-DOCTOR-20261121 \
  --serial SN-MES-DOCTOR-20261121 \
  --basic-user "$MES_USER" \
  --basic-pass "$MES_PASSWORD" \
  --execute \
  --confirm-write WO-MES-DOCTOR-20261121
```

### 4.4 安全边界

- 默认不访问网络；
- 只有 `--execute` 才写 MES；
- `--confirm-write` 必须与工单号完全一致；
- 使用 `WO-MES-DOCTOR-*` 和 `SN-MES-DOCTOR-*` 测试前缀；
- 不自动删除 MES 记录；
- 必须在 MES 沙箱或明确允许测试数据的工单范围内执行；
- 报告会记录测试数据责任提示。

### 4.5 结论解释

- `PASS`：同步回执、重复请求和冲突行为符合当前连接器契约；
- `WARN`：MES 基本可用，但业务键幂等或错误码不稳定，需要合同或适配器补强；
- `FAIL`：成功回执不合法，或非法请求被接受，不能直接进入生产；
- `DRY_RUN`：只生成测试计划，没有写入 MES。

## 5. 如何用工具扩业务

### 5.1 对 MES 厂商

可以把工具包装为：

- MES 连接器认证；
- 版本升级回归；
- 白标适配器自检包；
- 客户交付前预检。

MES 厂商每交付一个客户，都可以先跑一次契约体检。工具本身可以成为渠道合作入口。

### 5.2 对系统集成商

可以把工具纳入：

- 售前技术评估；
- 项目接口预检；
- 上线前验收；
- 故障复盘。

集成商最怕的不是代码难，而是接口反复试错。工具把试错变成报告和清单。

### 5.3 对工厂

工厂不一定为“连接器 SDK”付费，但可能为：

- MES 接入风险诊断；
- 断网和重复投递演练；
- 质量结果可追溯；
- 班次对账和异常处置；
- 上线前可靠性验收。

付费入口应该是结果和服务，而不是抽象技术组件。

## 6. 推荐的 90 天顺序

### 第 1～2 周

- 用契约体检工具接触 10 个 MES 厂商/集成商；
- 形成 3 份真实 MES 体检报告；
- 收集接口差异和常见错误码；
- 不新增视觉和 OEE 功能。

### 第 3～6 周（首版已完成）

- 本地操作台 MVP 已落地；
- 打通开始检测、完工、队列/死信和回执查看；
- 用真实客户场景做 5 次可用性测试。

### 第 7～10 周

- 做质量证据包；
- 关联 SN、图片、模型版本、correlationId 和 MES 回执；
- 形成客诉/审计演示。

### 第 11～13 周

- 选择一个存量设备场景，做 PLC/IO 或扫码适配；
- 只做一个协议，不做万能采集平台；
- 用一个付费诊断或试点验证覆盖价值。

## 7. 要监控的产品指标

- 首次拿到合法 MES 回执的时间；
- MES 接口联调人天；
- 契约体检发现的问题数；
- 单站实施人天；
- 配置化交付比例；
- 死信平均处置时长；
- 回执对账一致率；
- 操作员无需研发支持完成日常操作的比例；
- 证据包生成和查询时间；
- 同一适配器在第二个客户复用的比例。

## 8. 不做什么

- 不做通用低代码平台；
- 不做万能协议网关；
- 不恢复 OEE 和硬件主线；
- 不把 YOLO 当唯一卖点；
- 不免费为单个客户开发专属功能；
- 不在没有真实接口样本时构建大量 MES 适配器；
- 不用页面数量、代码行数或测试数量冒充产品价值。

## 9. 一句话结论

当前最值得做的不是“再加一个 AI 功能”，而是：

> **用 MES 契约体检把接入风险前置，用本地操作台把系统变得可用，用质量证据包把可靠性变成客户看得见的业务价值。**

这三项组合能把现有核心连接器从“技术闭环”推进到“能卖、能交付、能复用”的产品闭环。
