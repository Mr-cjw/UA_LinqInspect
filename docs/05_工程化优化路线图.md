# 工程化优化路线图

这份路线图同时服务两个目标：

- **作品集/答辩**：链路完整、口径清楚、能解释取舍、有可复现验证。
- **工厂试点**：异常可恢复、状态可观测、失败可处置、边界明确。

原则：不为了“看起来生产级”堆组件；每一层增强都必须能被测试和现场操作验证。

答辩脚本、试点阶段和对标分析见 [06_作品集答辩与工厂试点落地.md](06_作品集答辩与工厂试点落地.md)。

## 1. 现在处于什么阶段

当前项目应定位为 **可验证的 PoC+ / 试点前基线**，而不是纯演示 Demo：

- 业务链路完整：UA Variable/Method/Event → Node-RED → MES → UA 回执。
- 状态机明确：工单、缓冲队列、去重都有显式状态。
- 异常路径可验证：5xx、timeout、Method 拒绝已有自动化测试。
- 缓冲可恢复：Node-RED 使用 SQLite 事务队列，去重与入队原子提交，进程 `SIGKILL` 后可续传。
- 运行状态可查询：`GET /qc/status` 暴露队列、死信、心跳和模式状态；`GET /metrics` 提供 Prometheus 指标。

仍不具备的生产能力：

- OPC UA 证书、用户角色和网络边界。
- 真实 MES 沙箱的接收端幂等契约和跨进程 exactly-once（模拟 MES 已实现指纹冲突校验，当前只保证至少一次投递）。
- 真实视觉模型、模型版本治理和图像留存。
- HA、审计、集中日志、指标告警规则与完整灾备演练。

## 3. 验证口径

### 3.1 作品集/答辩验收

必须能现场演示：

1. 正常 NG 开单，`LastNgMesOrderNo` 出现 `MES-*`。
2. 完工报工，`LastCompletionReceiptNo` 出现 `RC-*`。
3. 5xx 进入死信，状态接口显示死信记录。
4. timeout 自动恢复后成功出队。
5. 不同工单开检被 Method 拒绝，当前工单不被覆盖。
6. 解释 `LastMesOrderNo` 为什么保留为兼容镜像。

### 3.2 工厂试点验收

必须补充：

1. 进程重启后队列恢复，且不重复开单/报工（本轮已完成）。
2. 企业 PKI、角色权限和证书轮换流程。
3. MES `4xx/429/5xx/timeout/非法 2xx` 分类处理（本轮已完成）。
4. 请求级 `correlationId` 串联 UA 事件、Node-RED 日志和 MES 日志（本轮已完成）。
5. 运行指标：队列深度、死信数、重试数、成功率、心跳失败数（Phase 2B 已完成）。
6. 断网/重启后的订阅恢复和 60 秒陈旧事件过滤验证（本轮已完成）。

## 4. 优先级路线

- 短断网、60 秒陈旧事件过滤、UA Server 重启订阅重建测试。

### P1：Phase 1 断网验证，已完成

1. ✅ **短时断网**
   - 已用 5 秒 `SIGSTOP/SIGCONT` 验证恢复后继续开检与完工。

2. ✅ **UA Server 重启**
   - 已用 `ServerStatus.StartTime`（`ns=0;i=2257`）变化触发显式重连，验证事件订阅重建。
   - 已验证 60 秒陈旧事件过滤和队列不失控。

3. ✅ **测试与文档收口**
   - 场景已纳入 `scripts/run_regression.py`；M3、运维加固、UA 写回确认、写回前崩溃恢复、事件 outbox、队列容量处置与模拟 MES 幂等合同加入后当前合并回归为 512/512 PASS。
   - 仍建议补 Wireshark 的 `CreateMonitoredItems`/`Publish` 证据，并做真实网络切换/长时断网。

### P2A：SQLite 事务队列，已完成

1. ✅ **队列迁移**
   - 队列、死信、去重均已迁移到 SQLite（WAL + `synchronous=FULL`）。
   - NG 唯一键为 `serialNumber + occurredAt`，报工为 `workOrderId`。
   - 保持单飞行发送泵；`SENDING` 超过 15 秒由看门狗恢复。
   - 旧 flow context 首次启动时在一个事务中导入并清空。
2. ✅ **崩溃恢复验证**
   - 在一条请求 `SENDING` 时对 Node-RED 发送 `SIGKILL`。
   - 同库重启后队列恢复、回执续写、无重复队列行、无新增死信。

3. ✅ **测试**

### P3：生产化，不建议现在做

- OPC UA 冗余、多工位、多租户。
- 历史数据库/时序数据库和高可用消息队列。
- 现场部署、OTA、远程配置、备份恢复。
- 合规审计、数据保留策略和安全渗透测试。

## 5. 建议的架构演进

```text
阶段 1（历史）：Node-RED flow context + localfilesystem
阶段 2（当前）：Node-RED + SQLite 事务队列
阶段 3（生产）：边缘服务 + 持久消息队列 + MES 网关 + 监控平台
```

注意：当队列、重试、审计、权限开始变复杂时，应把发送泵从 Function 节点抽成独立服务；Node-RED 继续承担编排和可视化，而不是承载全部生产逻辑。

## 6. 作品集与工厂试点如何共用一套成果

| 能力 | 作品集价值 | 试点价值 |
|---|---|---|
| 双回执变量 | 讲清语义边界 | 避免回执覆盖，支持追溯 |
| 故障场景测试 | 证明不是“只跑通正常路径” | 证明失败可处置 |
| 状态接口 | 现场展示运行状态 | 接监控和告警 |
| SQLite 事务队列 | 证明事务边界与崩溃恢复能力 | 去重/入队原子、失败可处置，仍需接收端幂等 |
| 安全/审计 | 体现工程边界 | 现场准入前提 |
| 真实模型接入 | 展示 AI 与 OT 融合 | 产生实际质检价值 |

## 8. 不要做的事

- 在真实模型尚未接入前，先引入复杂微服务。
- 为了“看起来安全”只打开证书开关，却不定义信任和角色。
- 仅凭 SQLite 或“至少一次投递”就声称 exactly-once；必须同时证明 MES 接收端幂等。
- 把 Node-RED 的调试注入当作生产控制接口。
- 把“收到 MES 回执”误写成“MES 已入库”。
