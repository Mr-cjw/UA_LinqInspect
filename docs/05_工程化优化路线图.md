# 工程化优化路线图

这份路线图同时服务两个目标：

- **作品集/答辩**：链路完整、口径清楚、能解释取舍、有可复现验证。
- **工厂试点**：异常可恢复、状态可观测、失败可处置、边界明确。

原则：不为了“看起来生产级”堆组件；每一层增强都必须能被测试和现场操作验证。

答辩脚本、试点阶段和对标分析见 [06_作品集答辩与工厂试点落地.md](06_作品集答辩与工厂试点落地.md)。

## 1. 现在处于什么阶段

当前项目应定位为 **可验证的 PoC+ / 试点前基线**，而不是纯演示 Demo：

- 业务链路完整：UA Variable/Method/Event → Node-RED → MES → UA 回执。
- 状态机明确：工单、缓冲队列、去重都有显式状态。
- 异常路径可验证：5xx、timeout、Method 拒绝已有自动化测试。
- 缓冲可持久化：Node-RED 使用 localfilesystem context，近实时落盘。
- 运行状态可查询：`GET /qc/status` 暴露队列、死信、心跳和模式状态。

仍不具备的生产能力：

- OPC UA 证书、用户角色和网络边界。
- 事务型队列和跨进程 exactly-once。
- 真实视觉模型、模型版本治理和图像留存。
- HA、审计、集中日志、指标告警。

## 3. 验证口径

### 3.1 作品集/答辩验收

必须能现场演示：

1. 正常 NG 开单，`LastNgMesOrderNo` 出现 `MES-*`。
2. 完工报工，`LastCompletionReceiptNo` 出现 `RC-*`。
3. 5xx 进入死信，状态接口显示死信记录。
4. timeout 自动恢复后成功出队。
5. 不同工单开检被 Method 拒绝，当前工单不被覆盖。
6. 解释 `LastMesOrderNo` 为什么保留为兼容镜像。

### 3.2 工厂试点验收

必须补充：

1. 进程重启后队列恢复，且不重复开单/报工。
2. OPC UA 证书信任和角色权限。
3. MES 返回 `429/5xx/timeout` 的分类处理。
4. 请求级 `correlationId` 可串联 UA 事件、Node-RED 日志和 MES 日志。
5. 运行指标：队列深度、死信数、重试数、成功率、心跳失败数。
6. 断网/重启后的订阅恢复和 60 秒陈旧事件过滤验证。

## 4. 优先级路线

### P0：已经完成，保持回归

- 双回执变量 + 兼容镜像。
- 空窗口 NgRate 语义统一。
- `/qc/status` 状态接口。
- localfilesystem context 持久化。
- 5xx/timeout/Method 故障测试。

### P1：下一轮，建议 1 周内完成

1. **correlationId 贯穿**
   - Node-RED 入队时生成 `corr-<uuid>`。
   - HTTP header `X-Correlation-Id` 同时携带。
   - 日志统一输出该 ID。

2. **MES 错误分类**
   - `4xx`：业务拒绝，不重试。
   - `429`：按 `Retry-After` 退避。
   - `5xx`/timeout：现有 1s/2s/4s 退避，超限死信。

3. **错误码与 schemaVersion**
   - 请求体增加 `schemaVersion: "1.0"`。
   - 响应增加稳定 `errorCode`：`INVALID_BODY`、`DUPLICATE`、`MES_UNAVAILABLE` 等。

4. **端到端自动化补强**
   - 将 `tests/fault_scenarios.py` 纳入一键脚本。
   - 增加“Node-RED 重启后非空队列恢复且不重复开单/报工”测试。
   - 增加“重复 NG 不重复入队/不合单”测试。

5. **安全基线**
   - OPC UA 证书与服务端信任列表。
   - 匿名用户只读；写操作需要角色。
   - `ResetCounters` 增加审计事件。

### P2：试点增强，建议 2~4 周

1. **SQLite 事务队列**
   - 把 `flow.buf` 迁移到 SQLite 表。
   - 唯一约束：NG 用 `serialNumber + occurredAt`，报工用 `workOrderId`。
   - 状态：`PENDING/SENDING/SUCCESS/DEAD`。
   - 保持单飞行发送泵。

2. **可观测性**
   - `/qc/status` 升级为 Prometheus 指标。
   - 增加队列深度、死信数、重试次数、MES 延迟、订阅心跳。
   - 结构化 JSON 日志 + 集中采集。

3. **M3 断网重连**
   - 短时断网：验证原会话恢复。
   - 长时断网/Server 重启：验证订阅重建和 60 秒陈旧事件过滤。
   - 抓包验证 `CreateMonitoredItems` 与 `Publish`。

4. **真实 AI 接入**
   - YOLOv8/ONNX 推理结果替换随机数据源。
   - 增加模型版本、阈值、推理耗时、图像 URI。
   - 误检样本回流和模型漂移监控。

### P3：生产化，不建议现在做

- OPC UA 冗余、多工位、多租户。
- 历史数据库/时序数据库和高可用消息队列。
- 现场部署、OTA、远程配置、备份恢复。
- 合规审计、数据保留策略和安全渗透测试。

## 5. 建议的架构演进

```text
阶段 1（当前）：Node-RED flow context + localfilesystem
阶段 2（试点）：Node-RED + SQLite 事务队列 / 或独立边缘发送服务
阶段 3（生产）：边缘服务 + 持久消息队列 + MES 网关 + 监控平台
```

注意：当队列、重试、审计、权限开始变复杂时，应把发送泵从 Function 节点抽成独立服务；Node-RED 继续承担编排和可视化，而不是承载全部生产逻辑。

## 6. 作品集与工厂试点如何共用一套成果

| 能力 | 作品集价值 | 试点价值 |
|---|---|---|
| 双回执变量 | 讲清语义边界 | 避免回执覆盖，支持追溯 |
| 故障场景测试 | 证明不是“只跑通正常路径” | 证明失败可处置 |
| 状态接口 | 现场展示运行状态 | 接监控和告警 |
| context 持久化 | 说明可靠性意识 | 降低重启丢失风险，仍需事务队列兜底 |
| 安全/审计 | 体现工程边界 | 现场准入前提 |
| 真实模型接入 | 展示 AI 与 OT 融合 | 产生实际质检价值 |

## 8. 不要做的事

- 在真实模型尚未接入前，先引入复杂微服务。
- 为了“看起来安全”只打开证书开关，却不定义信任和角色。
- 在 flow context 或其他非事务型队列基础上声称 exactly-once。
- 把 Node-RED 的调试注入当作生产控制接口。
- 把“收到 MES 回执”误写成“MES 已入库”。
