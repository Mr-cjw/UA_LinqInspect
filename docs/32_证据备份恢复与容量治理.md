# 证据备份、恢复与容量治理

> 日期：2026-11-22 ｜ 状态：Edge Core 数据库与图片文件联合备份/恢复 MVP，已加入容量硬限制和显式清理工具
>
> 原则：容量不足时失败关闭，不静默删除业务证据；恢复前先验证备份，替换前先保留安全快照。

## 1. 解决什么问题

质量证据包现在同时依赖：

- Edge Core SQLite 数据库；
- `evidence-images` 图片文件目录。

只备份 SQLite 会出现“数据库有图片记录、恢复后文件不存在”；只备份图片又缺少投递、回执和审计状态。

因此备份必须同时覆盖：

```text
edge-core.sqlite
data/evidence-images/
manifest.json
```

恢复时必须验证：

- 数据库 SHA-256；
- SQLite `integrity_check`；
- SQLite `foreign_key_check`；
- 必需表；
- 每张图片的 SHA-256；
- manifest 中图片数量、总字节和数据库记录。

## 2. 备份目录结构

```text
data/edge-backups/
└── edge-core-20261122-071500/
    ├── manifest.json
    ├── edge-core.sqlite
    └── images/
        └── d1/
            └── d126d6....png
```

manifest 记录：

- 备份 schema 和类型；
- 创建时间；
- 数据库文件、SHA-256、大小和表行数；
- 图片数量、总字节；
- 每张图片的 imageId、SHA-256、类型、大小、相对路径和创建时间。

## 3. 创建备份

```bash
.venv/bin/python scripts/edge_core_backup.py backup \
  --source data/edge_core.sqlite3 \
  --images data/evidence-images \
  --output-dir data/edge-backups \
  --keep 7
```

行为：

1. 使用 SQLite Online Backup API 复制一致性数据库；
2. 校验数据库完整性和必需表；
3. 逐张校验源图片 SHA-256；
4. 复制图片并再次校验；
5. 原子发布完整备份目录；
6. 按保留数量删除旧备份目录。

任何图片缺失或哈希不一致时，备份失败，不发布不完整目录。

## 4. 恢复备份

先停止 Edge Core、操作台和 UA 写回服务，避免运行中替换数据库。

Dry-run：

```bash
.venv/bin/python scripts/edge_core_backup.py restore \
  --backup data/edge-backups/edge-core-20261122-071500 \
  --target data/edge_core.sqlite3 \
  --target-images data/evidence-images \
  --dry-run
```

正式恢复：

```bash
.venv/bin/python scripts/edge_core_backup.py restore \
  --backup data/edge-backups/edge-core-20261122-071500 \
  --target data/edge_core.sqlite3 \
  --target-images data/evidence-images \
  --force
```

恢复行为：

1. 完整验证备份；
2. 在目标文件系统暂存数据库和图片；
3. 再次验证暂存内容；
4. 对现有目标创建 `edge-core-pre-restore-*` 安全快照；
5. 清理目标 `-wal/-shm`；
6. 替换数据库和图片目录；
7. 对恢复结果再次验证；
8. 失败时尝试从安全快照回滚。

没有 `--force` 时，现有目标不会被覆盖。

## 5. 容量治理

配置项：

```text
EDGE_EVIDENCE_IMAGE_MAX_BYTES=8388608
EDGE_EVIDENCE_IMAGE_MAX_TOTAL_BYTES=1073741824
EDGE_EVIDENCE_IMAGE_MAX_FILES=10000
EDGE_EVIDENCE_IMAGE_MIN_FREE_BYTES=268435456
EDGE_EVIDENCE_RETENTION_DAYS=90
```

上传图片时检查：

- 单图大小；
- 图片总数；
- 图片总字节；
- 图片目录所在文件系统的剩余空间；
- 磁盘最低保留空间。

任一限制不满足时：

- API 返回 `507 INSUFFICIENT_STORAGE`；
- 不写入文件；
- 不新增数据库记录；
- 不删除旧图片。

这是失败关闭，不会用静默淘汰换取“继续运行”。

## 7. 清理策略

清理只处理“超过保留期且没有被任何 delivery 引用”的图片。

默认 dry-run：

```bash
.venv/bin/python scripts/maintain_edge_evidence.py cleanup \
  --retention-days 90
```

确认后：

```bash
.venv/bin/python scripts/maintain_edge_evidence.py cleanup \
  --retention-days 90 \
  --apply
```

被 delivery payload 引用的图片不会被自动删除。已被审计证据引用的内容必须由归档和保留策略处理，不能靠容量清理绕过。

## 8. systemd 定时备份

新增：

```text
deploy/systemd/ua-linqinspect-edge-backup.service.in
deploy/systemd/ua-linqinspect-edge-backup.timer.in
```

默认每天 `02:45` 执行联合备份，并保留 7 份。

启用：

```bash
sudo systemctl enable --now ua-linqinspect-edge-backup.timer
```

## 10. 当前限制

- 备份 manifest 已支持 HMAC 签名，但备份文件本身尚未加密；
- 备份仍是本地目录，尚未异地复制或对象存储；
- 没有 WORM/不可变存储；
- 没有自动恢复演练定时器；
- 清理调度尚未默认启用；
- 图片魔数校验不等于完整内容安全扫描；
- 生产恢复仍要求人工停止服务并确认停机窗口。

备份解决“证据能不能回来”，容量硬限制解决“磁盘满了会不会悄悄删证据”，恢复前快照解决“恢复错了还能不能退回去”。
