## 0. 环境准备与导入

```powershell
cd D:\UA_LinqInspect

# 1. 重建隔离 Python 环境（已存在 .conda 时可跳过）
conda create --prefix .conda python=3.11 -y
& '.conda\python.exe' -m pip install -r 'server\requirements.txt'

# 2. 启动 UA Server（另开一个窗口）
$env:UA_ENDPOINT_PORT = "4840"
$env:QC_AUTO_INSPECT = "1"
$env:QC_NG_PROBABILITY = "0.5"
& '.conda\python.exe' 'server\qc_server.py'

# 3. 启动本地 Node-RED（再开一个窗口）
$env:APPDATA = "$PWD\.appdata"
$env:LOCALAPPDATA = "$PWD\.localappdata"
& '.node-red\node_modules\.bin\node-red.cmd' `
    --userDir "$PWD\.node-red" --port 1880 --no-telemetry
# 打开 http://127.0.0.1:1880，右上角菜单 → 导入 → 选择 nodered/flows.json → 部署
```

**导入注意**：`OpcUa-Event` / `OpcUa-Client` / `OpcUa-Endpoint` 三个节点的配置项随 node-red-contrib-opcua 版本略有差异。若导入后节点报"missing endpoint/配置丢失"，按以下关键参数手工核对：
- Endpoint：`opc.tcp://localhost:4840`，安全策略 None，模式 NONE
- OpcUa-Event：必须分别显式订阅 `ns=2;s=NgDetectedEventType` 与 `ns=2;s=WorkOrderCompletedEventType`。当前 Server + `node-red-contrib-opcua@0.2.355` 组合下，只订阅 BaseEventType（`i=2041`）可能收不到自定义字段。
- OpcUa-Client：由消息驱动，`action` 使用 `events` / `read` / `write` / `method`；Method 的入参放在 `msg.inputArguments`，不是 `callmethod` 或 `payload.inputArguments`。
- 订阅启动兼容：contrib 0.2.355 的首条 `events` 消息只建立 Subscription；`fn_sub_log_ng` / `fn_sub_log_done` 会在 5 秒后重发同一订阅消息，确保 Event MonitoredItem 真正挂载，请勿删除该逻辑。

## 1. 流的"边缘节点"设计要点（对应红线）

| 红线 | 流内实现（节点） |
|---|---|
| 契约强一致 | `fn_enq_ng`/`fn_enq_done` 报文字段与 M1 §3.1 逐字对齐，occurredAt 用 `new Date().toISOString()`（ISO8601 UTC 带 Z） |
| 报工唯一发令枪 | 仅 `WorkOrderCompletedEvent` → `fn_dedup_done` → 报工入队；流内无任何"数量够了自行报工"逻辑 |
| 缓冲状态机 | `fn_pump`/`fn_resp`：`PENDING → SENDING → SUCCESS(出队)/PENDING(退避)/FAILED(死信)`，**单飞行**（同一时刻仅一条在途，规避并发写回与 SQLITE_BUSY） |
| 超时与退避 | `fn_resp`：3 次、1s/2s/4s 指数退避；超限转 FAILED 死信 + error 红灯，不阻塞队列 |
| 防重 | 双侧：Node-RED `fn_dedup_ng`（serialNumber+occurredAt，serialNumber 兜底）/`fn_dedup_done`（workOrderId）+ MES 侧同指纹返回原单号 `duplicated:true` |
| Method 结果校验 | `fn_ua_result`：accepted=False → error 打印原因，**阻断后续动作** |
| 断网探测/心跳 | `inj_hb` 每 5s 读 DeviceStatus；`fn_ua_err` 连续 3 次异常判定假死并告警，成功响应由 `fn_ua_result` 清零 |
| 陈旧事件过滤 | `fn_parse`：事件 age>60s 丢弃，防 overflow 洪峰 |
| 告警削峰 | `fn_alarm`：10s 抑制窗合并计数，超窗一次性亮灯携带合并条数 |
| 回执落地 | `fn_resp` 成功分支写回 **`LastMesOrderNo`**（不覆盖 CurrentWorkOrderId） |

## 2. 四种验收场景（录屏/日志必须齐全）

### 场景①：正常 NG 流（正向）
1. 注入"正常"→ 点"开检 WO-20261109-001" → 等待 NG 事件（可将 Server 的 `QC_NG_PROBABILITY` 调高加速）
2. **预期**：MES 侧日志出现 `mesOrderNo`；`fn_resp` 打印 `[回执] MES工单号=... → 写回 LastMesOrderNo`；UaExpert 中 `LastMesOrderNo` 有值且 `CurrentWorkOrderId` 未被覆盖

### 场景②：MES 超时流（退避重试）
1. 注入"超时" → 触发 NG
2. **预期**：`fn_resp` 打印 3 次退避（status=0/超时，1s/2s/4s 间隔）；第 3 次重试时 MES 10s 后已恢复响应 → 成功出队（若 MES 持续超时则第 3 次后转 FAILED，见场景③）

### 场景③：MES 5xx 拒绝流（死信）
1. 注入"5xx" → 触发 NG → 等 3 次重试耗尽
2. **预期**：`[死信FAILED] ... 需人工处置` error 红灯；队列不再含该条；切回"正常"模式后**不再自动补发死信**（人工处置语义）

### 场景④：UA Method 拒绝流（阻断）
1. Server 运行中，先点一次"开检"，再**重复点"开检"（不同工单号需改 fn_call_start 内工单号）** 或在完工后再次点"完工"
2. **预期**：`[UA拒绝] rejected: ... —— 已阻断后续动作`；无任何 MES 报工/开单报文产生

### 附加（M3 正式验收，此处预演）
- **断网重连**：停掉 Node-RED 网络或重启 Server → 心跳告警 `[连接告警] 连续3次...` → 恢复后短时断网场景订阅应自动续推（ActivateSession 原会话）
- **陈旧事件**：重启 Server 前制造 NG，重启后观察 `陈旧事件丢弃` 日志（age>60s 的事件不入队）
