# 质量证据包与追溯

> 日期：2026-11-22 ｜ 状态：单条投递证据包 MVP，已接入 Edge Core API、本地操作台和真实在线链路演练
>
> 目标：从一个 `deliveryId` 或 `correlationId` 出发，还原某件产品为什么判 NG、消息何时进入队列、MES 返回了什么、UA 是否确认写回、是否发生重试或人工处置。

## 1. 解决什么问题

只看到“消息发送成功”不足以处理客户投诉、质量审计和现场争议。

现场真正需要回答：

- 这一件产品的 SN 和工单是什么？
- 缺陷类型、置信度和图片引用是什么？
- 用的是哪个模型、哪个数据集？
- 消息什么时候进入队列？
- MES 请求重试了几次？
- MES 最终回执号是什么？
- UA 回执写回是否确认？
- 是否进入过死信，由谁重放或确认？
- 整个过程中 correlationId 是否一致？

质量证据包把这些信息从现有持久化数据中重新组装，不复制一套业务状态。

## 2. 数据来源

证据包只使用已经持久化的数据：

- `deliveries.payload_json`：质检事件；
- `deliveries`：投递状态、尝试次数、MES 回执、UA 确认；
- `delivery_events`：状态迁移审计；
- `dead_letters`：死信、重放和人工处置记录；
- `metadata`：模型版本、模型哈希、数据版本、图片哈希等可选视觉血缘。

因此不会出现“证据系统显示成功，但实际投递状态不同”的第二套真相。

## 3. 证据包结构

```json
{
  "schemaVersion": "1.0",
  "bundleType": "QC_DELIVERY_EVIDENCE",
  "generatedAt": "...",
  "deliveryId": "...",
  "businessKey": "...",
  "correlationId": "...",
  "inspection": {},
  "visionLineage": {},
  "delivery": {},
  "mes": {},
  "ua": {},
  "audit": [],
  "deadLetter": null,
  "completeness": {},
  "limitations": [],
  "bundleSha256": "...",
  "bundleHashScope": "canonical-json-excluding-generatedAt-and-bundleSha256"
}
```

### 3.1 inspection

质检事实：

- sourceEventId；
- stationId；
- eventType；
- occurredAt；
- result；
- workOrderId；
- serialNumber；
- defectType；
- confidence；
- imageId；
- metadata。

### 3.2 visionLineage

视觉模型血缘：

- modelVersion；
- modelSha256；
- datasetVersion；
- imageSha256；
- imageHashScope；
- inferenceMs。

这些字段来自事件 `metadata`。没有真实视觉数据时字段为空，证据包不会伪造模型信息。

### 3.3 delivery 与 mes

投递状态和 MES 事实：

- state；
- attempts；
- nextAttemptAt；
- MES endpoint；
- mesReceipt；
- lastErrorCode；
- lastErrorMessage。

### 3.4 ua

UA 回执写回确认：

```json
{"writeConfirmed": true}
```

只有独立 UA 写回适配器成功调用 `RecordMesReceipt` 并通过 Edge API 回报后，才为 true。

### 3.5 audit

按顺序列出：

- PENDING → SENDING；
- SENDING → RETRY_WAIT；
- SENDING → UA_WRITE_PENDING；
- UA_WRITE_PENDING → DONE；
- 死信重放等状态变化。

每条都带时间和 correlationId。

### 3.6 completeness

明确告诉使用方：

- 哪些字段缺失；
- 是否字段完整；
- 图像二进制是否保存；
- 是否只有图片引用；
- 是否包含模型血缘。

当前 MVP 只保存 `imageId` 和哈希引用，不保存图片二进制。

### 3.7 limitations

证据包会明确说明：

- bundleSha256 是内容完整性哈希，不是数字签名；
- 图片二进制需要单独保留策略；
- 视觉指标只对对应模型版本和数据集有效。

## 4. bundleSha256

`bundleSha256` 对除 `generatedAt` 和 `bundleSha256` 自身以外的规范 JSON 计算 SHA-256。

作用：

- 多次读取时内容稳定可比对；
- 交接文件可检测意外修改；
- 可以作为后续审计归档的索引值。

不能把哈希说成签名或不可抵赖证明。若需要不可抵赖，必须增加签名、密钥管理和时间戳服务。

## 5. HTTP 接口

```text
GET /v1/deliveries/{deliveryId}/evidence
Authorization: Bearer <EDGE_API_TOKEN>
```

返回 `EvidenceBundle` JSON。

契约文件：

```text
contracts/evidence-bundle.schema.json
docs/api/edge-core.openapi.yaml
```

## 6. 本地操作台

最近投递表新增“证据”按钮。

点击后：

- 展示工单、SN、缺陷、置信度、图片引用；
- 展示模型版本和模型哈希；
- 展示 MES 回执和 UA 确认；
- 展示 correlationId 和 bundleSha256；
- 展示完整性结论；
- 可下载完整 JSON。

操作台代理接口：

```text
GET /api/evidence/{deliveryId}
```

浏览器仍然不直接持有 Edge API Token。

## 7. 视觉元数据接入

Edge Core 接受事件 `metadata` 对象。Node-RED 直写 Edge Core 时会保留以下可选字段：

- modelVersion；
- modelHash / modelSha256；
- datasetVersion；
- imageSha256；
- imageHashScope；
- inferenceMs；
- qualityGate；
- visionDecision；
- decisionReason。

真实视觉适配器或后续 YOLO/ONNX 推理模块应继续使用这些字段，不需要修改投递状态机。

## 8. 典型使用场景

### 客诉追溯

输入 MES 回执号或 correlationId，定位对应投递和证据包。

### 质量审计

检查 NG 是否有模型版本、图片引用、MES 回执和 UA 写回确认。

### 现场故障复盘

查看尝试次数、错误码、死信原因和人工处置记录。

### 客户验收

导出 JSON 证据包，与 MES 日志和质检记录逐笔核对。

### 责任边界

- 投递失败：查看 delivery、mes、audit；
- 视觉误判：查看 modelVersion、confidence、imageSha256 和图像质量门禁；
- 图片缺失：查看 imageBinaryStored 和采集端留存策略。

## 9. 当前测试

- Edge Core 证据包单测：覆盖 payload、视觉 metadata、MES 回执、UA 确认、状态审计、完整性、bundleSha256；
- 操作台证据代理：8/8 测试模块；
- 真实在线链路：19/19 PASS，包含真实 UA、Node-RED、Edge Core、MES 和 UA 写回后的证据包读取。

## 10. 当前限制

- 不保存图片二进制；
- 不提供数字签名；
- 没有独立证据归档设备；
- 没有客户级数据保留和销毁策略；
- 尚无长期对象存储、WORM 或时间戳服务；
- 视觉模型卡只对已记录的数据版本有效。

## 11. 下一步

1. 增加图片二进制保留根目录和生命周期策略；
2. 增加证据包签名或 HMAC；
3. 支持按工单、SN、MES 回执号查询；
4. 生成客户可读 PDF/HTML 证据摘要；
5. 接入真实视觉模型元数据和客户图片；
6. 在付费试点中验证证据包的审计价值。

## 12. 一句话

质量证据包把“可靠投递”从不可见的队列行为，变成客户可以查看、导出和对账的业务证据。
