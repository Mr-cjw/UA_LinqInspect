## 2. 高频问答

### Q1：为什么不用 REST 或 MQTT，而用 OPC UA？

项目要演示工业设备语义模型、Method 调用、Event 通知和 Subscription。OPC UA 同时提供地址空间、类型系统、事件、订阅和标准服务语义，适合设备侧与边缘侧交互。MQTT 更适合高频数据流，REST 更适合普通业务 API。

### Q2：为什么 NodeId 用字符串？

可读、易调试、便于教学和跨人协作。生产系统也可以使用数字 NodeId，但本项目优先可理解性。

### Q3：为什么自定义事件必须继承 BaseEventType？

这样客户端可以复用 OPC UA 的事件订阅模型，事件中包含标准字段（如 Message、Severity、SourceNode），同时通过 Property 扩展业务字段。

### Q4：为什么 NG 会收到两个事件？

`InspectionFinishedEventType` 表示“完成了一次检测”，无论 OK/NG 都会发；`NgDetectedEventType` 只在 NG 时额外发。前者用于全量统计，后者用于 NG 开单。

### Q5：为什么保留 `CurrentWorkOrderId`、`LastMesOrderNo`、`LastNgMesOrderNo`、`LastCompletionReceiptNo` 四个变量？

`CurrentWorkOrderId` 是派工单号，由我方/MES 下发并驱动状态机；`LastNgMesOrderNo` 是 NG 开单受理凭证，`LastCompletionReceiptNo` 是完工报工凭证。三者语义不同，混写会破坏工单状态和追溯关系。`LastMesOrderNo` 只是最近一次回执的兼容镜像，方便旧客户端读取，不能被新逻辑用来判断回执类型。

### Q6：为什么 `StartInspection` 要幂等？

消息重发或操作员重复点击很常见。同一工单重复开检应接受但不重置状态；不同工单则必须拒绝，避免覆盖当前生产批次。

### Q7：为什么 `CompleteWorkOrder` 要做多层校验？

完工是报工的唯一发令枪。如果工单不一致或设备不在 Running，继续报工会污染 MES 数据，所以必须先拒绝并给出原因。

### Q8：为什么需要单飞行发送泵？

同一时刻只允许一条请求在途，避免并发写回和队列状态竞争，也为未来 SQLite 单写者模型做准备。代价是吞吐量受限。

### Q9：为什么是 1s/2s/4s 退避，不是无限重试？

指数退避给 MES 恢复时间；有限重试避免队列永久阻塞。超限后进入死信，转为人工处置，不自动无限重发。

### Q10：为什么 `NgRate` 空窗口用 `-1.0`？

`0.0` 表示“有样本且没有 NG”，`-1.0` 表示“还没有样本”。两者语义不同，避免冷启动被误判为质量良好。

### Q11：为什么过滤 60 秒以上的事件？

断网恢复后可能收到大量积压事件，如果全部处理会造成洪峰和重复开单。超过 60 秒的事件直接丢弃，保护边缘队列。

### Q12：为什么去重要做两层？

Node-RED 去重防止重复入队，MES 去重防止网络重试导致重复生成业务单。两者指纹不同，形成防御纵深。

### Q13：为什么 Node-RED 不根据数量自行报工？

报工必须由 UA Server 的 `WorkOrderCompletedEvent` 驱动，保证唯一发令枪，避免边缘层猜测业务状态。

### Q14：超时和 5xx 的处理区别是什么？

两者都会进入退避重试；5xx 是服务端明确拒绝，超时是请求未按时完成。在本原型中两者都按失败重试处理，超时还依赖 Node-RED HTTP 3 秒超时和发送泵看门狗。

### Q15：当前项目有哪些生产化缺口？

无 OPC UA 证书和角色权限、flow context 不是事务型队列（不能宣称 exactly-once）、单工位、模拟 MES、无 Historical Access / Alarm & Condition、M3 断网重连与抓包尚未自动化验收。正常链路、5xx、timeout、Method 拒绝已有自动化证据。

## 3. 60 秒项目介绍

```text
我做了一个工业质检 OT-IT 闭环原型。虚拟质检数据写入 asyncua OPC UA Server，
Server 用 15 个变量表达设备状态、工单、检测结果、统计和 MES 回执，用 3 个 Method 管工单，
用 3 个继承 BaseEventType 的事件通知检测和完工。

Node-RED 作为边缘客户端订阅 NG 和完工事件，做解析、陈旧过滤、去重、告警削峰，
再进入单飞行缓冲队列，按 1s/2s/4s 退避调用模拟 MES，失败进入死信。
NG 回执写 LastNgMesOrderNo，完工回执写 LastCompletionReceiptNo，LastMesOrderNo 只做兼容镜像，绝不覆盖 CurrentWorkOrderId。

目前在 Ubuntu 上 M1 33/33、M2 正常链路 10/10、故障场景 19/19 通过。
```

## 4. 三分钟技术讲解结构

1. 业务目标：质检结果要进入 MES，但设备侧需要标准语义和可靠边界。
2. 信息模型：对象树、变量权限、Method 校验、事件类型。
3. 链路：UA 事件 → Node-RED 解析 → 队列 → MES → 回执。
4. 可靠性：去重、单飞行、退避、死信、陈旧过滤、心跳。
5. 验证：33 项 M1 冒烟测试 + 10 项 M2 端到端测试 + 19 项故障场景测试。
6. 边界与下一步：证书、持久化、M3 断网重连、真实 YOLOv8。

## 5. 练习任务

### 练习 1：新增缺陷码

修改 `server/qc_server.py` 的 `DEFECT_CODES`，同步更新 M1 文档。验证新码可以通过事件进入 Node-RED 和 MES。

### 练习 2：修改 NgRate 窗口

用 `QC_NG_WINDOW=5` 启动，产生 6 个样本，验证窗口只保留最近 5 个。说明为什么累计统计不受影响。

### 练习 3：观察双事件

把 `QC_NG_PROBABILITY` 设为 `1.0`，订阅两个事件，确认每次检测都产生 `InspectionFinishedEventType` 和 `NgDetectedEventType`，观察 SN 和 imageId 一致。

### 练习 4：制造 5xx 死信

注入 5xx，触发 NG，等待重试耗尽；检查 `flow.dead`。然后切回 ok，确认死信不会自动补发。

### 练习 5：实现 SQLite 持久化（进阶）

把 `flow.buf` 替换为 SQLite 表，增加唯一约束：

```text
NG:   serialNumber + occurredAt
完工: workOrderId
```

保持单飞行发送，验证 Node-RED 重启后队列可恢复。

### 练习 6：M3 断网重连

分两个子场景：

1. 秒级断网：观察是否在原会话上恢复订阅。
2. 长时断网或 Server 重启：观察订阅重建、60 秒陈旧事件丢弃。

记录 `CreateMonitoredItems` 和 `Publish` 请求/响应，作为抓包证据。
