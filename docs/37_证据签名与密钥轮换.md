# 证据签名与密钥轮换

> 日期：2026-11-22 ｜ 状态：质量证据包和备份 manifest 已支持 HMAC-SHA256，支持当前密钥、历史密钥和 CLI 验证
>
> 边界：HMAC 证明“持有共享密钥的一方生成的文档未被修改”，不是公开可验证的数字签名，也不是不可抵赖证明。

## 1. 为什么需要签名

`bundleSha256` 只能证明当前文件内容与哈希值一致，无法阻止攻击者同时修改内容并重算哈希。

因此增加基于共享密钥的 HMAC：

- 只有持有密钥的一方能生成合法签名；
- 内容任意变化都会导致验签失败；
- 导出证据包时可以交给客户、审计或运维复核；
- 备份 manifest 同样可以签名，恢复前先验签。

## 2. 签名结构

证据包增加：

```json
{
  "signatureStatus": "SIGNED",
  "signature": {
    "algorithm": "HMAC-SHA256",
    "keyId": "primary",
    "value": "64位十六进制HMAC",
    "scope": "canonical-json-excluding-signature"
  }
}
```

签名规则：

1. 删除顶层 `signature` 字段；
2. 对剩余 JSON 按 key 排序、紧凑编码；
3. 使用当前 keyId 对应的密钥计算 HMAC-SHA256；
4. 将 64 位十六进制结果写回 `signature.value`。

未配置签名密钥时：

```json
{
  "signatureStatus": "UNSIGNED",
  "signature": null
}
```

## 3. 配置

```bash
export EDGE_EVIDENCE_SIGNING_KEY='replace-with-at-least-32-random-bytes'
export EDGE_EVIDENCE_SIGNING_KEY_ID='primary'
```

历史密钥只用于验证旧证据：

```bash
export EDGE_EVIDENCE_SIGNING_PREVIOUS_KEYS='{"2026-q4":"old-secret","2026-q3":"older-secret"}'
```

规则：

- 新签名只使用 `EDGE_EVIDENCE_SIGNING_KEY` 和对应 keyId；
- 验证时可以接受当前密钥和历史密钥；
- 历史密钥不能用于新签名；
- 历史密钥不应无限期保留，需按审计保留期管理。

## 4. 密钥轮换流程

推荐顺序：

1. 生成新随机密钥；
2. 把旧密钥放入 `EDGE_EVIDENCE_SIGNING_PREVIOUS_KEYS`；
3. 将当前密钥替换为新密钥，并更新 keyId；
4. 重启 Edge Core 和备份服务；
5. 验证新证据使用新 keyId；
6. 验证旧备份仍可用历史密钥通过；
7. 根据审计周期下线过期历史密钥。

禁止：

- 把密钥写入代码仓库；
- 在日志或错误消息中打印密钥；
- 删除旧密钥后仍保留需要验证的旧证据；
- 把 HMAC 描述成非对称数字签名。

## 5. 命令行验证

```bash
.venv/bin/python scripts/verify_evidence_signature.py \
  --file exported-evidence.json
```

验证签名备份目录：

```bash
.venv/bin/python scripts/verify_evidence_signature.py \
  --backup-dir data/edge-backups/edge-core-20261122-130508
```

输出：

```json
{
  "ok": true,
  "signatureStatus": "SIGNED",
  "algorithm": "HMAC-SHA256",
  "keyId": "primary",
  "scope": "canonical-json-excluding-signature"
}
```

也可直接验证备份：

```bash
.venv/bin/python scripts/edge_core_backup.py verify \
  --backup data/edge-backups/edge-core-20261122-130508
```

## 6. 备份签名

联合备份 manifest 现在也带：

- `signatureStatus`；
- `signature.algorithm`；
- `signature.keyId`；
- `signature.value`。

恢复前的验证顺序：

1. 读取 manifest；
2. 验 HMAC；
3. 验证数据库 SHA-256；
4. 验证 SQLite 完整性；
5. 验证所有证据图片 SHA-256；
6. 创建目标安全快照；
7. 替换数据库和图片目录；
8. 恢复后再次验证。

如果系统配置了签名密钥，但备份是 `UNSIGNED`，恢复会拒绝，避免无签名备份被误认为可信。

## 8. 能力边界

### HMAC 能证明

- 文档由持有对应共享密钥的一方生成；
- 文档在签名后未被修改；
- 验证方知道使用的是哪个 keyId。

### HMAC 不能证明

- 对不知道共享密钥的第三方公开证明来源；
- 签名方不能否认自己签过；
- 证据产生时间可信；
- 密钥持有者没有在签署前篡改原始数据。

如果需要更强边界，需要：

- Ed25519/ECDSA 非对称签名；
- 私钥硬件保护或 HSM；
- 可信时间戳服务；
- WORM 归档；
- 审计日志和密钥轮换记录。

## 10. 一句话

HMAC 让证据包从“哈希可对账”升级为“持有密钥可验真”，但它是共享密钥完整性机制，不是神话级的不可抵赖数字签名。
