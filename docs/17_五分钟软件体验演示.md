# 五分钟软件体验：没有硬件，先验证最值钱的部分

> 日期：2026-11-21 ｜ 定位：PoC+/付费试点前软件演示 ｜ 不需要 OPC UA 硬件、PLC 或真实 MES

## 1. 先看一句话

一条 NG 从质检系统出来，经历 MES 超时、边缘服务重启、MES 持续故障、死信人工重放，
最后只产生一张 MES 业务回执，并在 OPC UA 写回确认后进入 `DONE`；
每一步都能用 `correlationId`、`deliveryId` 和 SQLite 状态轨迹查清楚。

这不是再做一个视觉模型，而是解决“质检结果如何可靠进入 MES”的最后一公里。

## 2. 三十秒启动终端演示

在仓库根目录执行：

```bash
.venv/bin/python scripts/demo_edge_core.py
```

生成完整证据报告：

```bash
.venv/bin/python scripts/demo_edge_core.py --report .tmp/demo-evidence.md
```

需要给投资人看可视化界面：

```bash
.venv/bin/python scripts/demo_edge_core.py --ui --no-open
# 浏览器打开 http://127.0.0.1:8899/
```

如果本机有桌面浏览器，可以去掉 `--no-open` 自动打开。页面右上角的按钮会重新跑一遍，
并在页面内展示队列、死信、MES 回执和完整审计轨迹。

## 3. 演示会发生什么

| 步骤 | 发生了什么 | 投资人应该看到的价值 |
|---|---|---|
| 1 | 质检站产生一条 NG | 输入是标准业务事件，不绑定某一家视觉硬件 |
| 2 | API 先写 SQLite Outbox，再异步投递 | MES 是否在线，都不会让 NG 直接丢失 |
| 3 | 同一 NG 重复上报 | 幂等键命中，队列仍是 1 条，不重复开单 |
| 4 | MES 超时 | 任务进入 `RETRY_WAIT`，不会误判成功 |
| 5 | 真正关闭并重建 Edge Core 服务 | 同一 SQLite 中的任务原样恢复 |
| 6 | MES 返回 503，重试预算耗尽 | 任务进入 `DEAD`，错误码和尝试次数可查 |
| 7 | MES 恢复，人工重放死信 | 复用原业务键、原业务标识和审计记录 |
| 8 | MES 返回合法回执 | 回执校验通过后进入 `UA_WRITE_PENDING` |
| 9 | OPC UA 写回确认 | 只有写回成功才进入 `DONE` |

本演示中死信前累计 3 次失败尝试；人工重放后第 4 次投递成功。系统承诺
**at-least-once + 业务幂等**，不承诺 exactly-once。

## 4. 哪些是真的，哪些是模拟的

| 部分 | 本演示 | 说明 |
|---|---|---|
| HTTP API | 真实 `edge_core/api.py` | 使用公开的 `POST /v1/inspection-events`、死信重放和 UA 写回接口 |
| SQLite Outbox | 真实 `edge_core/store.py` | WAL、事务入队、业务键唯一约束、状态迁移和审计表 |
| 投递 Worker | 真实 `edge_core/worker.py` | 超时/5xx 重试、4xx 死信、回执校验、租约和状态机 |
| 服务重启 | 真实重建 API 服务 | 新进程实例重新打开同一 SQLite 文件 |
| MES | 本地模拟 HTTP 服务 | 明确标为模拟，不冒充客户 MES；支持超时、503、成功和幂等回执 |
| OPC UA 写回 | Demo 本地模拟确认调用 | 独立生产适配器已具备真实安全 OPC UA Method 集成；Demo 为保持无硬件体验仍使用本地模拟 |
| 硬件 | 不需要 | 这是软件先行的核心价值：硬件采购前先验证可靠性与流程 |

## 5. 对投资人的 60 秒说明

> 工厂通常已经有视觉、人工质检和 MES，真正难的是让 NG 结果可靠进入业务系统：
> MES 会超时、网络会断、设备会重启，人工还要对账。我们做的不是又一个视觉算法，
> 而是质检结果进入 MES 的可靠连接器：先持久化、幂等去重、有界重试、死信人工重放、
> 回执校验、UA 写回确认，全链路用 correlationId 对账。
>
> 现在还没有硬件，但今天这个 Demo 已经用项目真实代码跑通了最值钱的部分。
> 下一步不是继续堆功能，而是拿 2～3 个真实工位做付费试点，用客户 MES 沙箱验证
> 接口合同、恢复时间和交付人天。硬件到了只是换接入层，不会推翻已经验证的软件底座。

## 6. 这个 Demo 证明了什么，没有证明什么

已经证明：

- 重复上报不会重复入队；
- 超时和 5xx 会保留原任务并进入有界重试；
- 服务重启后任务仍能从 SQLite 恢复；
- 重试耗尽会进入可见、可重放的死信；
- 人工重放不改变原业务键；
- MES 合法回执与 UA 写回都完成后才进入 `DONE`；
- 每一步都有持久化状态轨迹。

尚未证明：

- 真实客户 MES 的幂等合同和接口兼容性；
- 真实 OPC UA 设备、PLC 和产线节拍下的现场稳定性；
- 真实断网切换、抓包、文件系统配额和生产网络时延；
- 付费意愿、交付人天、回款和跨客户复制。

这些正是付费试点要验证的内容，不能用一个本地 Demo 冒充生产验收。

## 7. 自动化验证


## 8. 演示之后的商业动作

1. 用本 Demo 约见 2～3 家已有 MES 的江西本地制造企业或 MES 集成商；
2. 不收“无限免费 POC”，只做有期限、有验收数据、有启动款的付费试点；
3. 现场只接一个工位、一种工单和一类 MES 接口；
4. 用真实 MES 沙箱复验同一幂等合同、故障恢复和回执对账；
5. 用试点数据更新单位经济模型，再决定是否投入硬件和视觉增值模块。
